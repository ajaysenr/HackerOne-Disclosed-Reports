## Vulnerability Details

## Summary

When one curl invocation (or one libcurl handle) does two SFTP/SCP transfers to the same host, the second transfer reuses the first SSH connection even when it asks for a different host key with `--hostpubsha256` (`CURLOPT_SSH_HOST_PUBLIC_KEY_SHA256`). The second transfer never checks its pin and succeeds against a key it would reject on a fresh connection.

`ssh_config_matches()` in `lib/url.c` compares only the private and public key file names:

```c
return sshc1 && sshc2 && Curl_safecmp(sshc1->priv_key, sshc2->priv_key) &&
       Curl_safecmp(sshc1->pub_key, sshc2->pub_key);
```

The host-key requirements are not part of the match. From reading the code, the same applies to `--hostpubmd5` and to the known_hosts file (`CURLOPT_SSH_KNOWNHOSTS`); I tested only the SHA256 pin.

## Affected

- curl 8.23.0 and master at a40772f2f9, libssh2 backend (libssh2 1.11.1), Linux.
- Not tested with the libssh backend.

## Reproduce

Any SSH server with password login. `BAD` is a pin that does not match the server key.

```sh
BAD=AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=
GOOD=<the server's real SHA256 host key, base64>

# wrong pin alone: refused
echo data | curl -s -u t:pw --hostpubsha256 "$BAD" -T - sftp://localhost/tmp/alone.txt; echo "exit $?"

# good pin, then wrong pin on the same command line
echo data | curl -v -u t:pw --hostpubsha256 "$GOOD" sftp://localhost/etc/hostname -o /dev/null \
  --next -u t:pw --hostpubsha256 "$BAD" -T - sftp://localhost/tmp/reused.txt; echo "exit $?"
```

Result on both versions:

```
exit 60                                            <- wrong pin alone
* SSH: SHA256 checksum match                       <- first transfer, good pin
* Reusing existing sftp: connection with host localhost
exit 0                                             <- second transfer, wrong pin
/tmp/reused.txt written, /tmp/alone.txt not written
```

The attached `repro-sftp.sh` does the same and reads `GOOD` from curl's own mismatch message.

## Impact

An application that sets a host-key pin per transfer on a shared handle or connection pool can send data to, or accept data from, a server that the later transfer's pin excludes. Example: a multi-tenant uploader that pins each destination's key, where a tenant controls one key pinned for the same host name and port.

The attacker must own the server (or its key) for the first, accepted transfer to the same host and port. So I think severity is low to medium.

This looks like the same class as CVE-2023-27538 (SSH connection reuse ignores config changes). That fix added the key file names, but not the host-key checks.

## Suggested fix

Store the host-key settings (`SHA256` and `MD5` pins, known_hosts file) in the SSH connection meta and compare them in `ssh_config_matches()`, or refuse reuse when any of them differs.
