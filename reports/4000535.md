## Vulnerability Details

### Summary

I found a local-resource restriction bypass in Burp Community's `Save OpenAPI requests to site map` action.

The validator and click parser select different OpenAPI-shaped objects from the same HTTP response. A nested OpenAPI 3.0 `swaggerDoc` object makes the action available, but the click handler parses the top-level OpenAPI 3.1 object. In the 3.1 schema, a local `file:///` URL in `$id` becomes the base for a fragment-only `$ref`.

Burp rejects the equivalent direct `file:///...#/secret` `$ref` as an external API definition. The `$id` plus fragment-only form passes that check. Burp then opens the local JSON schema and copies its selected `example` value into the generated POST body.

I reproduced this through the normal Community UI in fresh Temporary Projects on:

- 2026.8 build 53343, Early Adopter
- 2026.7.3 build 52685, Stable

The two runs used different ports, local filenames, and markers. Both markers appeared in Burp-generated requests. I sent each generated request once through Repeater to a loopback collector and received HTTP 200.

Community does not send the generated request automatically. The local read happens after the user selects the site-map action. Disclosure to the definition-selected server requires a later explicit send of that generated request.

### Steps to reproduce

Everything in the attachment binds to `127.0.0.1`.

1. Extract `PZ-BURP-002-h1-attachments.zip` and enter its `repro` directory.

2. Check the supplied response shapes:

```bash
python3 -B verify_shapes.py
```

Expected output:

```text
REPRO_SHAPES=PASS
```

3. Start the loopback fixture:

```bash
python3 repro_server.py --mode exploit --schema local-schema.json
```

It prints a random `definition_url`. Keep this process running.

4. Start Burp Community in a fresh Temporary Project. Configure a loopback Proxy listener on port 8081, or use the supplied settings:

```bash
java -jar /absolute/path/to/burpsuite_community.jar --config-file=community-8081-project.json
```

5. Replace `<PORT>` with the port printed in step 3, then fetch the response through Burp:

```bash
curl --noproxy '' --proxy http://127.0.0.1:8081 -H 'X-HackerOne-Research: 1rhino2' http://127.0.0.1:<PORT>/openapi.json
```

6. Open Target > Site map and select the `GET /openapi.json` response.

7. Open the Response message-actions menu and click `Save OpenAPI requests to site map`.

8. Burp adds `POST /collect` to the site map. Its body contains `PZ_UI_POSITIVE_ONE_91c7e2`.

The marker is absent from the HTTP definition response. Before Burp processes that response, the fixture supplies it only through `local-schema.json`.

9. Send the generated POST to Repeater and click Send once. The fixture returns HTTP 200 and records:

```text
REQUEST=POST /collect
BODY={"leak":"PZ_UI_POSITIVE_ONE_91c7e2"}
HTTP_LOG="POST /collect HTTP/1.1" 200 -
```

10. Repeat with Community 2026.7.3 in another fresh Temporary Project. My second run used a separate local file and produced the marker `PZ_UI_POSITIVE_TWO_4ad93b`.

### Controls

Stop the previous fixture with Ctrl-C before changing modes. Each new fixture prints a new random port and truncates `server.log`, so use the newly printed port each time. I used a fresh Temporary Project for every control.

Direct external reference:

```bash
python3 repro_server.py --mode direct-control --schema local-schema.json
```

The action is visible, but Burp rejects the definition with:

```text
This definition can't be uploaded as it links to one or more external API definitions. Review the definition and remove the external links.
```

No collector request is generated and the fixture receives no POST.

`$id` without the fragment reference:

```bash
python3 repro_server.py --mode id-only-control --schema local-schema.json
```

Burp generates only `{"control":"INLINE_ONLY"}`. After one Repeater send, the collector receives that exact inline value. No `PZ_UI_POSITIVE_` marker appears in the generated request or receipt.

Top-level 3.1 object without the `swaggerDoc` bridge:

```bash
python3 repro_server.py --mode root-only-control --schema local-schema.json
```

The same top-level 3.1 candidate is present, but the response menu does not contain `Save OpenAPI requests to site map`.

### Root cause and evidence

Inspection of the packaged classes with `javap -p -c` matches the UI result:

1. `validate()` unwraps `swaggerDoc` and reports a valid 3.0.0 document.
2. The click path calls `parse()` on the original body. That path selects the top-level 3.1 object.
3. The external-reference check scans `$ref`. It rejects the direct `file:///...` control, accepts `#/secret`, and does not reject the local base in `$id`.
4. The bundled 3.1 resolver rebases the fragment against `$id` and reaches its local file reader.
5. The selected schema `example` is used in the generated POST body.

The attachment includes the two UI runs, both collector receipts, the three controls, successful `openat` lines for both positive local files, parser-selection output for both builds, and the packaged-bytecode notes.

Tested JAR hashes:

- 2026.8 build 53343: `888f0588cf82a3b70d508dcbf07591184a26249e38cda8ea8b5a68f4b5a30789`
- 2026.7.3 build 52685: `c8262dc5426f38bedc490d66c5d21b6ff77d6dc6d85cefe6a66c882690134069`

### Limits

- The local path must be known or guessed and readable by Burp.
- The confirmed target is a compatible JSON schema.
- The selected fragment must be schema-shaped.
- The proof confirms disclosure of a selected `example` value. It is not an unrestricted raw-file read.
- Windows, macOS, and Burp Professional were not tested.
- No integrity or availability impact is claimed.

## Impact

If the user invokes `Save OpenAPI requests to site map` on the malicious response, Burp reads the selected `example` from the known, readable local schema and places it in a generated request addressed to the server selected by the definition. The server receives the value only if the user later sends that generated request.

Local OpenAPI and JSON Schema files can contain internal endpoint examples, sample credentials, tokens, tenant identifiers, or other non-public test data in `example` fields. My proof uses only synthetic markers and does not claim access to files without a compatible schema shape.

PortSwigger's current program treats websites accessed through Burp as untrusted and lists local-file retrieval by such a website as a Medium example. The required interaction is unlikely, so I am selecting Medium under the program's reduced-bounty interaction category.
