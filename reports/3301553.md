## Vulnerability Details

## Summary

Any authenticated user can lock or unlock files they do not own by targeting absolute WebDAV paths of other users. The DAV plugin resolves files from the absolute request URI without verifying that the `<userId>` path segment matches the authenticated session user. This enables:

- Cross-user manual locks : attacker locks a victim's files, blocking writes (PUT/MOVE/DELETE, editor saves).
- Lock-token disclosure: the app returns the lock token to unauthorized callers, enabling them to remove token-based locks (client locks) of other users.

This is exploitable in default Docker dev setups and standard deployments where the `files_lock` app is enabled.

- Nextcloud instance with `files_lock` enabled.
- Two valid users (victim `alice` and attacker `admin` below). Any authenticated user works; admin is not required.

Exploit A: Cross-user lock DoS (attacker locks Alice’s file)

## Steps to reproduce 

1) Nextcloud installed
2) Enable the app: `docker exec -u www-data nextcloud php occ app:enable files_lock`.
3) Create users (e.g., `alice`, `admin`).
4) Run the script.
5) Verify the demonstration visiting alice account and see the lock icon on file and open it and try to write somethng it , you won't because it is locked by attacker.



## What’s happening under the hood

- The DAV plugin calls `getFileFromAbsoluteUri($requestUri)` which parses `/remote.php/dav/files/<userId>/<path>` and directly opens `<userId>`’s folder, ignoring the authenticated session user.
- Therefore a logged-in user can operate on `/files/alice/...` while authenticated as `bob/admin`, applying user-locks to Alice’s files.
- On unauthorized unlock attempts, the app constructs and returns lock properties including the `lock-token`, leaking it to the attacker, who can then send a standard `UNLOCK` with that token to clear the lock.

## Prerequisites for exploitation

- Attacker has any valid Nextcloud account (no admin required).
- Attacker can reach the DAV endpoint (default `/remote.php/dav`).
- Attacker can guess or observe a victim username and file path. In practice user IDs and paths are often predictable or discoverable.

## Recommended remediation

1) Enforce user scoping in DAV handlers:
   - In `lib/DAV/LockPlugin.php` `httpLock/httpUnlock`, do not use `getFileFromAbsoluteUri` blindly. Either:
     - Resolve nodes in the context of the session user, or
     - Parse the path `<userId>` and verify it equals `IUserSession->getUser()->getUID()`. If mismatch, return 403/404.

2) Harden `getFileFromAbsoluteUri`:
   - Verify the extracted `<userId>` equals the current session user and/or perform proper permission checks. Reject otherwise.

3) Do not disclose lock tokens to unauthorized callers:
   - Remove token from `getLockProperties()` and OCS `unlocking()` responses unless the caller is authorized.

## Impact

- Any user on a multi-tenant Nextcloud can cause widespread write-denial by locking other users’ files at will (single request per file), disrupting collaboration and automation (desktop/mobile clients, online editors, CI pipelines writing into user folders).
- The lock token (credential-like secret) for token-based client locks is exposed to unauthorized users, allowing them to remove locks placed by client apps, increasing friction and risking data loss due to concurrent edits.
- No social engineering, special setup, or elevated privileges are required beyond having an account and guessing/knowing the victim username and a path.
