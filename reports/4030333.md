## Vulnerability Details

## Summary:
During a file upload, curl mishandles HTTP/2 RST_STREAM received from the server (with reason HTTP_1_1_REQUIRED or REFUSED_STREAM) leading to a use after free of a `struct Curl_easy` object. The control flow is a bit complicated, so I've produced an ASCII tree of the control flow to highlight the object lifetime issue in the Appendix below.

Preconditions for this are `curl -T <file>`, where `<file>` contains anywhere "<word> <word> <any>\n\n" and exceeds ~135KB. Our PoC exploit also requires `-Z`/`--parallel` when PIE/ASLR is enabled, but this is not necessary to trigger the memory corruption, only for exploitation.

As for how the UAF happens, after receiving the reset, multi.c converts the reset into a retry and calls `multi_done()`. In `multi_done()`, it calls `Curl_conn_ev_data_done()` which makes curl forget about the transfer, then it calls `Curl_req_done()`. Then `Curl_req_done()` flushes the buffered unsent remainder of the upload body into the connection. Since curl no longer knows about the transfer, it treats those bytes as a new request.  If they look like a request line, `h2_submit()` opens a new stream that stores a pointer to the `Curl_easy` object. This is the pointer that will be UAFed. After the retry completes, the application frees the `Curl_easy` object, but the connection still holds the pointer. It is dereferenced when the server sends a frame on that stream which can happen at exit, when the connection pool is destroyed.

## Affected version
8.22.0

## Steps To Reproduce:
I've attached a malicious server that triggers the bug (`evil-server.py`)

```bash
wget 'https://curl.se/download/curl-8.22.0.tar.gz'
sha1sum curl-8.22.0.tar.gz # should be 284e444b67f676a281906cfc86e9672780555cd4
tar xf curl-8.22.0.tar.gz
mkdir build ; cd build
# build with ASAN enabled
CC=clang CFLAGS="-O2 -g -fsanitize=address"" LDFLAGS="-Wl,-rpath,/opt/curl-release/lib" \
    ../curl-8.22.0/configure --prefix=/opt/curl-release \
      --enable-static --enable-shared --disable-docs --disable-manual \
      --with-openssl --with-zlib --with-brotli --with-zstd --with-libidn2 \
      --with-nghttp2 --with-libpsl --with-libssh2 --with-gssapi \
      --enable-ldap --enable-ldaps --enable-websockets --enable-mqtt --enable-ipfs \
      --enable-ntlm --enable-smb --enable-httpsig --enable-httpsrr --enable-ssls-export \
    && make -j"$(nproc)"
# make an example file for uploading that satisfies the conditions for the UAF
cat ../docs/*.md > sample_docs.md
# start the malicious server, see attached evil-server.py
 python3 evil-server.py &
# we use --insecure because the server's cert is self signed, not necessary to trigger the bug.
# This should result in an ASAN UAF crash
./src/curl --insecure -T ./sample_docs.md https://127.0.0.1:19170/x
```

I've also attached a .tar.gz that contains scripts to build a Docker container where you can reproduce the RCE.

It also contains a suggested patch (basically, call `Curl_req_abort_sending()` when retrying the connection to discard unsent request content).
