## Summary

The June 2026 symlink/containment hardening for the translation **ZIP download** (GHSA-xwj4-fp82-r2rj / CVE-2026-61792, commits `299fb28` + `33a9acb`) introduced `VCS_METADATA_DIRS` in `weblate/utils/files.py` to strip VCS metadata directories from downloaded archives. The set only contains `(".git", ".hg")`. **Subversion (`.svn`) and Bazaar (`.bzr`) metadata are missing**, even though:

1. Weblate documents Subversion as an officially supported VCS (`docs/vcs.rst` → "Subversion", incl. a "Subversion credentials" section), and
2. Weblate's *own* copy logic treats `.svn`/`.bzr` as VCS metadata: `weblate/trans/component_copy.py:109` uses `shutil.ignore_patterns(".git", ".hg", ".svn", ".bzr")`.

As a result, `is_vcs_metadata_path()` returns `False` for `.svn/...` and `.bzr/...`, so any `.svn` or `.bzr` tree present inside a component (committed by any user with push access, or accidentally committed during an SVN→Git migration — a well-known real-world occurrence) is bundled verbatim into the downloaded ZIP, including the SQLite working-copy database `wc.db` (repository layout, URLs, revision mappings) and any `.svn/auth/` credential-cache files that found their way into the tree. Git and Mercurial equivalents are correctly excluded — the differential is directly observable with a one-line expression (see Step 3).

I am deliberately reporting this as an **incomplete-hardening / defense-in-depth gap** rather than the credential-theft scenario that motivated my initial test: the containment layer added in the same fix blocks *cross-component* symlink escapes (verified, see Step 4), Weblate's SVN backend is git-svn (no `.svn` directory is created in working trees), and the SVN auth cache lives in `DATA_DIR/home/.subversion` — outside component roots. The concrete, reproducible impact is: **VCS metadata that the June 2026 fix was designed to exclude still ships in ZIP downloads when a component contains `.svn`/`.bzr` data**, which is a completeness gap in a security-fix mechanism and is inconsistent with the project's own ignore-set in `component_copy.py`.

## Suggested fix

`weblate/utils/files.py`, line 36 — one line:

```python
VCS_METADATA_DIRS = frozenset((".git", ".hg", ".svn", ".bzr"))
```

This matches the set already used by `weblate/trans/component_copy.py:109` (`shutil.ignore_patterns(".git", ".hg", ".svn", ".bzr")`). `is_vcs_metadata_path()` casefolds its input, so case variants (`.SVN`, `.SVn`) are covered automatically. A regression test asserting the `.svn`/`.bzr` ZIP-exclusion parity with `.git`/`.hg` would lock this in (existing coverage only exercises `.git`: `weblate/utils/tests/test_files.py`; there is currently no test for `.svn`/`.bzr`).

## Impact

- Any user with access to a component's ZIP download (the `translation.download` permission — the same threat model the June 2026 advisory was fixed for) can obtain a component's **full Subversion or Bazaar metadata** if such data exists in the tree: repo layout and URL (`wc.db` REPOSITORY table), working-copy state, and any `.svn/auth/svn.simple` credential-cache entries that were ever committed into the tree.
- This is a **completeness gap in a shipped security fix**: the June 2026 hardening explicitly guarantees VCS metadata is stripped from downloads, and it silently fails for two of the four VCS metadata types the project itself recognizes in `component_copy.py:109`. The `main` branch currently ships this state; the same incomplete set also feeds `vcs/base.py:898`, `validators.py:372`, `tasks.py:985`, and `discovery.py:629`, so symlink resolution, path validation, backup, and component discovery all share the inconsistency.
- I am *not* claiming remote credential theft on stock installs: Weblate's SVN support is git-svn (`docs/vcs.rst`), which creates no `.svn` folder in the checkout (metadata lives under `.git/svn`, already excluded), and the SVN auth cache (`DATA_DIR/home/.subversion/auth`) lives outside any component root. Reproducible impact is the metadata-disclosure/incompleteness above; on self-hosted deployments that previously used direct SVN working copies or that committed `.svn`/`.bzr` directories into Git (a documented, common migration accident), the leaked ZIP contents additionally include the stored `svn.simple` auth blobs for that repository.

Suggested severity: **Low–Medium** (needs an authenticated user, needs attacker-influenced repo content, disclosure is within the same component root; overriding factor is that it defeats a security mechanism explicitly introduced by CVE-2026-61792 and is trivially fixable).
