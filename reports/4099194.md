## Vulnerability Details

## Summary:
When curl is built with GnuTLS, a malicious WebSocket server can make `curl -T <file> wss://...` send memory past curl's WebSocket send buffer. This is due to an out of bounds read in `gtls_send()`, which doesn't handle if `gnutls_record_send()` returns a number of bytes sent greater than the number of bytes it was given to send. GnuTLS does that after a blocked send. It takes two sends from different buffers to trigger, so I added an ASCII illustration of the control flow in the appendix to make it easier to follow.

GnuTLS is required for this bug, It doesn't work on OpenSSL. It also requires an upload of a few MB or more to a `wss://` URL on the attacker's server. So I'm submitting this as a Low.

As for how it happens, the server first stops reading, so curl's upload blocks on a full socket. The last `gnutls_record_send()` has by then encrypted a 16384 byte record that the socket doesn't take. GnuTLS keeps it and returns `GNUTLS_E_AGAIN`, and those bytes stay in curl's request buffer to be passed in again. The next `gnutls_record_send()` call sends the kept record and returns its length (16384) whatever buffer and length it was given. Normally that call is for the same bytes so it's ok. But if the server sends a WebSocket PING, curl answers with a PONG and `ws_flush()` sends it straight from the WebSocket send buffer, ahead of the request buffer. So the next call is `gnutls_record_send(PONG, 10)` and it returns 16384. There is a check here in `gtls_send()` but it's only a `DEBUGASSERT`. On a release build it just adds 16384 to the buffer pointer, subtracts it from the 10 bytes left, which wraps around and keeps looping. So then `gnutls_record_send()` encrypts and sends the next 16384 bytes of memory after the PONG until the socket is full again. The server can control how much it reads based on how much it reads before the PING. If the read gets to the end of the heap, curl segfaults.

For applications using curl as a library, if they call `curl_easy_send()` with a shorter buffer after `CURLE_AGAIN`, the same thing can happen. For example `curl_easy_send(buf, 5, &n)` can return `CURLE_OK` with `n` getting 131072.

## Affected version
8.22.0

## Steps To Reproduce:
The attached `evil-server.py` is a malicious server that triggers the bug. The script below should also reproduce the bug

```bash
wget 'https://curl.se/download/curl-8.22.0.tar.gz'
sha1sum curl-8.22.0.tar.gz # should be 284e444b67f676a281906cfc86e9672780555cd4
tar xf curl-8.22.0.tar.gz
mkdir build ; cd build
# build with GnuTLS instead of OpenSSL
CC=clang CFLAGS="-O2 -g" LDFLAGS="-Wl,-rpath,/opt/curl-gnutls/lib" \
    ../curl-8.22.0/configure --prefix=/opt/curl-gnutls \
      --enable-static --enable-shared --disable-docs --disable-manual \
      --with-gnutls --without-openssl --with-zlib --with-brotli --with-zstd --with-libidn2 \
      --with-nghttp2 --with-libpsl --with-libssh2 --with-gssapi \
      --enable-ldap --enable-ldaps --enable-websockets --enable-mqtt --enable-ipfs \
      --enable-ntlm --enable-smb --enable-httpsig --enable-httpsrr --enable-ssls-export \
    && make -j"$(nproc)"
# a 32 MB file of one repeated byte, so that anything else the server receives is easy to spot
head -c 33554432 /dev/zero | tr '\0' A > As.bin
# start the malicious server, see attached evil-server.py (put it in this directory)
python3 evil-server.py & sleep 1
# we use --insecure because the server's cert is self signed, and -sS to keep the progress meter out of
# the server's output. Neither is necessary to trigger the bug.
./src/curl --insecure -sS -T As.bin wss://127.0.0.1:19239/
```

The PoC server looks at what it receives and if it prints if it gets something it wasn't supposed to (not part of the uploaded file).

Record 3's bytes are given to GnuTLS in phase 1 and are meant to be offered again, from `req.sendbuf`, by the next call. In phase 2 the PONG gets there first, GnuTLS answers for record 3, and `gtls_send()` applies that answer to the PONG's buffer.

Disclosure of client process memory to a malicious `wss://` server, for libcurl built with GnuTLS (default on Debian and Ubuntu?), while uploading a file to that server. The server can control how much to read
