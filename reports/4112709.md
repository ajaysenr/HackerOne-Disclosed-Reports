## Summary:
ssh_force_knownhost_key_type() in lib/vssh/libssh2.c compares a `[name]:port` known_hosts entry, the form ssh writes for non-default ports, with `strncmp(store->name + 1, conn->origin->hostname, kh_name_size)`. kh_name_size is the length of the name in the entry, so this is a prefix match: `[10.0.0.1]:2222` also matches 10.0.0.12, and `[git.example.co]:2222` also matches git.example.com. If such an entry for another host comes before the host's own entry with a different key type, curl forces that other key type for the connection. An attacker's server simply offers that type. The later check in ssh_knownhost() then finds no entry of that type for the host: with libssh2 1.11.1, libssh2_knownhost_checkp() only reports MISMATCH for a key of the same type. CURLOPT_SSH_KEYFUNCTION is therefore told CURLKHMATCH_MISSING instead of CURLKHMATCH_MISMATCH, which is the outcome of CVE-2026-87865, reached through plain entries instead of hashed ones; the code comes from 272282a054 (curl 7.69.0).

I would have liked to report this sooner, before 8.23.0 was out, but I've only managed to finish this now and I still have a lot of other curl CVEs to fix for the Debian package.

## Steps To Reproduce:
Copy the attached `test3990.pl` to tests/libtest/, and `test3990` and `test3991` to tests/data/. test3990 runs against the test suite's SFTP server, which has an RSA host key by default, with this known_hosts file:

```
[127.0.0]:PORT ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIAqmXRY8k+W9GtpWxYru6ELAXYHdXqjf33ziITGTiJUN
[127.0.0.1]:PORT ssh-rsa <the server's real key>
```

```
cd tests && ./runtests.pl 3990 3991
```

test3990 fails, and its trace shows curl taking the `[127.0.0]` entry for 127.0.0.1:

```
SSH: found host '127.0.0.1' in 'log/known3990'
SSH: set 'ssh-ed25519' as hostkey type
Failure establishing ssh session: -5, Unable to exchange encryption keys
```

The handshake fails only because the test server has no ed25519 key; a man-in-the-middle server would offer one. test3991 is the control. Its first entry is for `[127.0.0.1.2]:PORT`, which is not a prefix of the host, so curl forces ssh-rsa and the transfer works.

## Impact

## Summary:
An attacker who can intercept connections can target a host whose name extends an earlier `[name]:port` entry with the same port, which is most likely with IP addresses such as 10.0.0.1 and 10.0.0.12. An application whose CURLOPT_SSH_KEYFUNCTION callback trusts new hosts would then accept the attacker's key instead of rejecting a mismatch, and authenticate to the attacker. The conditions are otherwise those of CVE-2026-87865: the libssh2 backend and an application-provided key callback. Without an attacker it is also a functional bug. A legitimate connection to such a host fails, either at key exchange or because its key is reported as missing, as in the test above.
