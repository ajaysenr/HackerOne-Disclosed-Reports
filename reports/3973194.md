## Vulnerability Details

## Summary

`Curl_fopen()` copies the old cookie jar's permission bits onto a newly created temp file, but the temp file may receive a different GID (the process's primary group instead of the old file's group). After rename, group-permission bits that were intended for one group now authorize a different group. A local attacker in the new group who could not access the jar before curl ran can read persisted cookies (mode `0640`) or inject cookies (mode `0660`) afterward, without needing write access to the directory.

This regresses the safety property introduced for CVE-2022-32207. The original fix (`20f9dd6bae`) created the temp file as `0600` and applied the old mode via `fchmod()` only when both UID and GID matched. Commit `03cb1ff4d629` (curl 8.5.0) removed that guard entirely. Commit `8deaf04febba` (curl 8.20.0) re-added a UID check but never restored the GID check.

## Root cause

In `lib/curl_fopen.c`:

```c
if(sb.st_uid != geteuid())
  sb.st_mode = 0;
/* ... */
fd = curlx_open(tempstore, O_WRONLY | O_CREAT | O_EXCL,
                S_IRUSR | S_IWUSR | sb.st_mode);
```

Only UID is guarded. The old file's group bits are passed through to `open()` unconditionally. On Linux, in an ordinary (non-setgid) directory, the kernel assigns the process's primary GID to the new file. If that GID differs from the old file's GID, the surviving group bits now authorize a different set of users. `cookie_output()` then renames the temp file over the jar, making the change permanent.

## Affected versions

curl 8.5.0 through 8.21.0, plus affected 8.22.0 prerelease/development versions. The partial correction in 8.20.0 does not validate the GID.

## Reproduction

1. Build an affected curl release, starting with 8.5.0, on a POSIX system where newly created files normally receive the process's effective or primary GID.
2. Create two groups, group A and group B.
3. Create a victim user whose primary group is group B and who is also a member of group A.
4. Create an attacker user who belongs to group B but not group A.
5. Create a directory owned by the victim that both users can traverse but only the victim can modify.
6. Inside that directory, create a valid cookie jar owned by the victim and group A with mode `0640`, and place a recognizable test cookie in it.
7. Confirm that the attacker cannot read the cookie jar and cannot write to its containing directory.
8. Run curl as the victim with a nonrestrictive-enough umask such as `0022`, loading and saving the same jar through `CURLOPT_COOKIEFILE` and `CURLOPT_COOKIEJAR`, or the equivalent `-b jar -c jar` options.
9. Allow curl to complete a benign request so that it writes a sibling temporary file and renames that file over the original cookie jar.
10. Inspect the replacement file's UID, GID, and mode.
11. Observe the vulnerable result: the owner and `0640` mode are retained, but the GID changes from group A to the victim's primary group B.
12. Confirm that the attacker can now read the replacement jar and recover the recognizable cookie despite having no access before curl saved it.
13. Repeat the setup with an original cookie jar owned by group A at mode `0660`, and run curl as the victim with a umask such as `0002`.
14. Confirm that the replacement jar receives group B while retaining group-write permission.
15. As the attacker, append a syntactically valid cookie to the jar, then run curl again as the victim with that jar as input and output.
16. Confirm that curl loads and persists the attacker-injected cookie.
17. Repeat the read test with a restrictive `0077` umask and verify that the replacement becomes `0600`, preventing attacker access.
18. Repeat with the original jar already assigned to group B and verify that curl does not introduce access for a new principal.
19. Repeat in a setgid directory that causes the sibling file to inherit group A and verify that the attacker remains unable to read it.
20. Confirm a fix by creating the sibling as `0600`, inspecting its actual ownership, and copying group permission bits only when its GID matches the original file's GID.
21. Repeat the mismatched-GID tests and verify that saving the jar grants neither new read nor new write access to the attacker.

### Expected result

Replacing a cookie jar must not transfer its group permissions to a different group. Users who could not access the original file must not gain access after curl saves it.

### Vulnerable result

Curl copies the old mode bits to a sibling file without preserving or validating its GID. After rename, the same group permissions apply to a different group, granting new local read or write access.


## Impact

- **Confidentiality**: a local user who could not read the cookie jar before can read persisted cookies after curl saves.
- **Integrity**: with group-write bits, the attacker can inject cookies that curl subsequently loads and re-saves.
- The attacker does not need write access to the directory containing the jar.

The preconditions are restrictive (multi-user system, mismatched GIDs, surviving group bits, traversable path), so I expect Low severity at most.

## Suggested fix

Create the temp file as `0600`. After creation, `fstat()` the descriptor and copy group permission bits only when the temp file's GID matches the old file's GID. This restores the safety property from the original CVE-2022-32207 fix.

## Impact

## Summary:

A local attacker who belongs to the replacement file’s new group may gain access to a cookie jar they previously could not read or modify. They can potentially steal authentication cookies and hijack sessions or inject cookies that curl later sends to remote services, even without write permission to the directory containing the jar.
