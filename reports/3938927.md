## Vulnerability Details

### Summary

An organization admin on RubyGems.org can create an attacker-controlled organization owner through the gem transfer flow, then use it to evict the organization's legitimate owners and members and remove the publishing rights their memberships carried. The normal membership route prevents an admin from inviting an owner.

This is the RubyGems.org service, reviewed at `4e36c18deef651564e7029ad8c00594f7e207d1b` (`master`, 2026-07-30). I rechecked it on 2026-08-14 against `origin/master` at `257b9c548449fe35c398421e160c472483e151a7`, 33 commits later: every controller, model and policy cited below is unchanged, the line numbers still match, and no advisory or merged private fork covers it.

### Steps to reproduce

**Setup.** Three accounts:

- `founder` is Acme's legitimate organization owner. Acme owns `organization_gem`, and that membership is `founder`'s only route to publishing it.
- `attacker_admin_account` is a confirmed Acme organization admin and the direct owner of `transfer_gem`, a gem belonging to no organization. That ownership is what lets it start a transfer.
- `second_attacker_account` is a second account held by the same attacker. It holds no Acme membership and is a direct maintainer of `transfer_gem`.
- Each account holds a `push_rubygem` API key. Both attacker keys also carry `add_owner` and `remove_owner`, so the 403 in step 2 is the policy refusing and not a missing scope.

1. As `attacker_admin_account`, invite `second_attacker_account` as **Owner** at `/organizations/acme/memberships/new`. Returns **404**, and the members page does not list them.

2. As the same admin, add `second_attacker_account` as a direct owner of `organization_gem`. Returns **403**.

```sh
curl -i -X POST -H 'Authorization: attacker-admin-key' \
  --data-urlencode 'email=second_attacker_account' \
  --data-urlencode 'role=owner' \
  http://localhost:3000/api/v1/gems/organization_gem/owners
```

3. As the same admin, open `/gems/transfer`. Choose Acme, select `transfer_gem`, and on the **Owners** step set `second_attacker_account` to **Owner**. Finalize. Acme's members page now lists `second_attacker_account` as a pending **Owner**, the grant that was refused in step 1.

4. As `second_attacker_account`, accept at `/organizations/acme/invitation`. It is now a confirmed Acme owner.

5. Push `organization_gem` with `founder`'s key. Returns **200**.

6. As `second_attacker_account`, add itself as a direct Owner of `organization_gem` at `/gems/organization_gem/owners` and confirm the ownership through the emailed token.

7. As `second_attacker_account`, delete `founder` from Acme's members page. Only the two attacker-controlled accounts remain.

8. Re-push `organization_gem` with `founder`'s key from step 5. Returns **403**.

9. Push `organization_gem` with `second_attacker_account`'s key. Returns **200**.

The attached test walks the same sequence against a fuller organization: a second owner holding both a membership and direct gem ownership, an admin and a maintainer, all four evicted, and their direct roles on `organization_gem` removed.

### Where the check is missing

`app/policies/membership_policy.rb:10-13` is the intended boundary. It requires an existing organization owner when the role being granted is owner:

```ruby
def create?
  minimum_required_role = membership.owner? ? :owner : :admin
  organization_member_with_role?(user, minimum_required_role) || deny(t(:forbidden))
end
```

The transfer path authorizes `OrganizationPolicy#add_gem?` instead, which requires only admin, and then never consults `MembershipPolicy`. `app/controllers/rubygems/transfer/confirmations_controller.rb:8-14` runs that organization check and calls `transfer!`. `app/controllers/rubygems/transfer/users_controller.rb:26-28` permits `invites_attributes[id, role]`. `app/models/organization_invite.rb:12-20` copies the selected role into a new `Membership`, and `app/models/rubygem_transfer.rb:18-21` appends it to the organization.

Commit `0f40f5cb` (2026-05-22) added this authorization to the direct members controller, with regression tests for both routes, including `POST /organizations/:organization_handle/members as an admin inviting an owner is forbidden`. The transfer controller was not covered by that fix.

At review time the [transfer guide](https://guides.rubygems.org/organizations/transferring-gems/) allowed admins to initiate a transfer and assign the owner role, while the [member-management guide](https://guides.rubygems.org/organizations/managing-members/), `MembershipPolicy` and those May tests all reserved owner grants for owners.

### Demonstrated result

| Check | Before | After |
|---|---:|---:|
| Admin creates an organization Owner directly | 404 | created through transfer instead |
| Admin adds a direct owner to `organization_gem` | 403 | new Owner adds it |
| `founder` publishes `organization_gem` | 200 | 403 |
| `second_attacker_account` publishes `organization_gem` | no membership or gem role | 200 |

The attached integration test runs this sequence against a clean local test database at the reviewed commit: 1 test, 55 assertions, 0 failures, 0 errors, 0 skips, through the real router, controllers, policies and database state. ## Impact

This is an admin-to-owner privilege escalation, organization takeover and targeted publisher lockout. An organization admin can use gem transfer to create an organization owner, although `MembershipPolicy#create?` and the direct membership endpoint require an existing owner for that grant. Via their added account, the attacker can remove every legitimate owner, admin and maintainer. On the demonstrated organization gem, it can add attacker direct ownership and remove the legitimate direct roles.

The founder's push key returns 200 before its membership is removed and 403 afterward, and the attacker owner then publishes with 200. The attached integration test extends the same sequence to a fuller organization: a second owner holding both a membership and a direct gem ownership also goes from 200 to 403 once both grants are removed, and an untouched direct ownership on the transferred gem still returns 200. Lockout is limited to organization membership and the direct grants the attacker removes. The initial admin could already publish and yank organization gems; the added effect is excluding legitimate publishers and their owner-level recovery paths.
