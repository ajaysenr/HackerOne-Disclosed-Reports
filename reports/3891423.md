## Vulnerability Details

**Description:**
The `aws___run_script` tool of the [AWS MCP Server](https://docs.aws.amazon.com/agent-toolkit/latest/userguide/mcp-server.html) executes caller-supplied Python inside a hardened sandbox in a Lambda function named `CodeModeSandbox`. The sandbox has two layers: a static AST validator that blocks dangerous imports, builtins and attribute-access patterns, and a runtime layer that replaces builtins with proxies and restricts `open()`.

I found a complete escape of that sandbox. It yields arbitrary command execution as the Lambda user, filesystem read, disclosure of the sandbox's own source code, and disclosure of the Lambda execution role credentials.

The chain combines two things:
1. `match/case` **class patterns** (Python 3.10+) performs an implicit `getattr()` at the C level, which the AST validator never sees because it is not an attribute access or a `getattr()` call in the user's source.
2. The runtime layer's own type-proxy (`_safe_type` in `safe_exec.py`) hands user code a **mutable heap type** in place of the immutable `types.FunctionType`. That is what lets the exploit assign `__match_args__` onto the function type which is an assignment CPython itself refuses, and the one operation the whole chain depends on. Outside the sandbox, in normal Python 3.10+ environments, the same line raises `TypeError: cannot set '__match_args__' attribute of immutable type 'function'`.

The AST validator blocks:
- dot-notation dunder access -> `obj.__class__`
- `getattr()` calls -> `getattr(obj, "__class__")`
- `operator.attrgetter` -> the `operator` import is blocked

However, it does not block writes to `__match_args__` and it does not inspect the implicit `getattr()` performed by `MatchClass`. This gives the arbitrary attribute reads on any object.

## Steps To Reproduce:

The attached harness reproduces this end to end. It talks to the endpoint the same way a coding agent does using `uvx mcp-proxy-for-aws`, SigV4-signed with local AWS credentials.
**Prerequisites:** Python 3.10+, [`uv`](https://docs.astral.sh/uv/) installed (for `uvx`), and AWS credentials for any identity entitled to call the MCP endpoint. I used a dedicated least-privilege IAM user (`████████`).

1. Unzip the attached `pentest-harness.zip` and install the client.
```bash
unzip pentest-harness.zip
cd pentest-harness
python -m venv .venv && source ./venv/bin/activate
pip install -r requirements.txt
```

2. Configure AWS credentials (env vars, `~/.aws/`)
3. Run the single command inside the endpoint:
```bash
python3 rce.py --endpoint https://aws-mcp.eu-central-1.api.aws/mcp --region eu-central-1 'id'
```
It returns `uid=993(sbx_user1051) gid=990 groups=990` confirming that we are able to execute the `id` command on the system.
Executing the `env` command similarly returns the Lambda execution role's `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_SESSION_TOKEN`.

### What couldn't be exploited
- No cross tenant or cross session access: Each MCP session gets its own container.
- Lambda role credentials have blanket explicit `Deny *` blocking every AWS API call I tried across 30+ services. Only `sts:GetCallerIdentity` works, which as per AWS documentation cannot be denied.
- No network egress.
