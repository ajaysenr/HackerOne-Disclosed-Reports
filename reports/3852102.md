## Vulnerability Details

## Summary

A revoked deployment collaborator can regain access to private collaboration data after another active collaborator interacts with the deployment toolbar.

After a collaborator is revoked, their previously issued authorization token becomes invalid and requests correctly return `403 Forbidden`.

However, when an active collaborator performs a normal toolbar interaction, the previously revoked token becomes authorized again. The revoked user can then use the same token to access the Replicache synchronization endpoint and retrieve private deployment collaboration data, including comment threads and messages.

The revoked user is not re-invited and no new authorization is granted.

## Remediation

* Ensure that revoked collaborator authorization state is checked during every authenticated request.
* Immediately invalidate all authorization state associated with revoked collaborators.
* Prevent collaboration synchronization systems from restoring permissions from stale authorization data.
* Ensure cached membership states are invalidated after collaborator removal.
* Do not allow revoked tokens to regain access after unrelated collaborator activity.

## Impact

A user who has been explicitly removed from a deployment can regain access to private collaboration resources using an already revoked token.

This allows a previously revoked collaborator to:

* Read private deployment comments.
* Monitor collaboration activity.
* Access deployment collaboration state without being re-invited.
* Besides accessing message he can interact with the deployment like any invited user

The issue breaks the expected security guarantee of collaborator revocation, where removed users should immediately lose access to protected resources.
