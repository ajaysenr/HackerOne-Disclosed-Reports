## Vulnerability Details

Asset: https://github.com/WeblateOrg/website, the code behind the weblate.org customer portal.

## Summary

Removing an owner from a customer account on weblate.org deletes the row from `Customer.owners`, but it leaves `Customer.user_id`, the id of the user who created the customer, unchanged. `fosdem_donation()` and `get_customer()` look the customer up by that id and add the requester back as an owner:

```python
customer = Customer.objects.get_or_create(
    origin=PAYMENTS_ORIGIN,
    user_id=request.user.id,
    defaults={"email": request.user.email},
)[0]
customer.owners.add(request.user)
```

So whoever created a customer account can always get back in. In my test the remaining owner did everything the portal offers to revoke access: they removed the creator and pressed "Refresh token" so the old activation token stopped working. The creator then opened `/en/fosdem/donate/?amount=30` once and was an owner again. That request sends no invitation, needs no consent, sends no e-mail and writes no log entry. Back as an owner, the creator saw the new token on `/en/user/` and removed the owner who had removed them.

Reproduced on WeblateOrg/website main @ 7d0a3f762 (2026-10-16), on a local instance only.

## Why this is a security boundary and not intended behaviour

- b726a3ffd makes owners explicit peers with full control and adds audited removal. The owners box on the account page says owners control "billing, services, secrets, and other owners. Only add people you trust."
- 550fe33a0 ("fix(security): require consent for customer owners") means a new owner has to accept an invitation first.
- The project's own test `test_owner_can_remove_original_owner` (tests.py:1688) removes exactly the user this bug lets back in. Its fixture stores `user_id=owner.pk`, which is what production stores.

The `user_id` path skips both controls.

## The defect

- `views.py` `customer_owner()` L1234-1246: removal calls `owners.remove(owner)` and logs an interaction. `user_id` is not touched.
- `views.py` `fosdem_donation()` L1673-1693: neither `@login_required` nor POST-only. For any logged-in user it runs the re-add shown above, whatever the user owns at the time.
- `views.py` `get_customer()` L186-205: when the requester owns no customer, which is the state removal leaves them in, it falls through to the same re-add. It is called from `DonateView`, `subscription_new`, `AddDiscoveryView` and `DiscoveryRegistrationView`, so the normal donate, subscribe and discovery flows re-add the user as well. The regression tests cover the donate form too.

Every self-service customer is created through `get_customer()` with `user_id` set to the buyer, so this affects every self-service customer.

## Steps to reproduce

Two weblate.org accounts: alex creates the customer, and bianca is the second owner.

1. alex buys a subscription or makes a donation. The customer is stored with `user_id = alex`.
2. alex invites bianca on the owners form, and bianca accepts the e-mailed invitation.
3. bianca removes alex. alex now gets 404 on `/en/customer/<id>/`, and the token is gone from alex's `/en/user/`.
4. bianca presses "Refresh token" on the service. The old token now gets 404 from `/api/support/`.
5. alex opens `https://weblate.org/en/fosdem/donate/?amount=30`. It redirects to a payment page, and nothing has to be paid.
6. alex gets 200 on `/en/customer/<id>/` again, and `/en/user/` shows the new token.
7. alex removes bianca, and bianca now gets 404.

The run against a local server, from attachment 01:

```
# 3. bianca removes alex
bianca POST /en/customer/1/owners/             302 -> /en/user/ owner=1&remove=1
alex   GET  /en/customer/1/                    404 <- alex no longer has access
       activation token on alex's /en/user/: none
# 3b. bianca completes the revocation: rotates the activation token alex had seen
bianca POST /en/subscription/token/1/          302 -> /en/user/ Refresh token
       token before pz33sE... after XcGhSA...
anon   POST /api/support/                      404 with the old token <- revoked
# 4. alex is re-added by one GET (no CSRF token, no invitation)
alex   GET  /en/fosdem/donate/?amount=30       302 -> /en/payment/302a6208-.../
alex   GET  /en/customer/1/                    200 <- owner again
       activation token on alex's /en/user/: XcGhSA...  <- the rotated token
       e-mails sent by step 4: 0
# 5. alex removes bianca
alex   POST /en/customer/1/owners/             302 -> /en/user/ owner=2&remove=1
bianca GET  /en/customer/1/                    404 <- bianca locked out
```

The customer's interaction log afterwards (attachment 02) has bianca removing alex and then alex removing bianca, with nothing in between. Anyone reading the CRM sees a non-owner removing an owner.

The same checks as Django tests (attachment 06, results in 03):

| test | main @ 7d0a3f762 | with fix |
|---|---|---|
| removed owner opens /fosdem/donate/, must stay removed | FAIL | ok |
| removed owner submits the donate form, must stay removed | FAIL | ok |
| removed owner must not be able to remove the remaining owner | FAIL | ok |

## Remediation

1. Minimal fix (attachment 05): when the removed owner's id matches `user_id`, set `user_id` to -1. With this applied the three tests pass and the HTTP run stops at step 5 (attachment 04).
2. Better: in `get_customer()` and `fosdem_donation()`, find the customer only through `Customer.objects.for_owner(request.user)`, and create a new customer otherwise. Remove the same `user_id` fallback from `can_download_payment_invoice()`.
3. Customers whose creator was removed before the fix still have a stale `user_id`. A data migration that sets `user_id = -1` wherever that user is no longer an owner fixes them.

## Impact

Removing someone is how a customer takes away their access. The person this bug brings back is the one most likely to be removed: whoever set up the account. That is usually an employee who bought the subscription and later left, or an agency that bought it for a client and handed it over.

The obvious objection is that a former owner already saw everything. The reproduction answers that: bianca took every revocation step the portal offers, removal and token rotation, and alex still came back with the new token. Back as an owner, alex can:

- regain full owner rights with one GET. The remaining owners are not told, and the CRM log has no entry for it.
- get the service activation token even after it has been rotated (shown). They can also rotate it themselves, which disconnects the customer's own Weblate instance from its support subscription: step 3b shows that a rotated-out token gets 404 from `/api/support/`.
- read and change the customer's billing details (company name, address, VAT ID, billing e-mail) on `/en/customer/<id>/`, turn off recurring payments so subscriptions lapse, and download agreements and invoices.
- remove every remaining owner (shown). The paying customer then has no access to their own account until Weblate staff restore it.

Severity: C:H and I:H, because the attacker has full owner rights over billing data, service tokens and the owner list. I scored AC:H instead of AC:L because the attacker has to be the account's creator and has to have been removed. That gives 6.8, Medium.
