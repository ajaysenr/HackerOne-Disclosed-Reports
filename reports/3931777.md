## Vulnerability Details

## Description:

The client-side-media-processing endpoint `POST /wp/v2/media/<id>/finalize` writes attacker-supplied
strings **verbatim** into the attachment's `_wp_attachment_metadata`, including the top-level `file`
key and `sizes[*]['file']`. There is no `sanitize_callback`, no `pattern`, no `sanitize_file_name()`,
no basename check anywhere on that path.

`wp_delete_attachment_files()` has exactly one branch — the `$backup_sizes` branch — that derives
**both the file to delete and the directory used to confine the deletion** from `$meta['file']`.
Because the attacker controls `$meta['file']`, the `wp_delete_file_from_directory()` containment
check compares the target against a directory the attacker also chose, so the guard is a no-op. Every
other branch derives its confinement directory from `get_attached_file()` and is correctly confined;
only this one is not.

The `$backup_sizes` array is populated by `wp_ajax_image_editor()` (`edit_post` + a nonce that
WordPress prints to the Author itself in the media popup), which copies the attacker's poisoned
`sizes[*]` entry into the protected `_wp_attachment_backup_sizes` meta verbatim.

Net effect: an Author deletes any file the PHP process can unlink, anywhere on disk.

### 4. Sink — the only unconfined branch of `wp_delete_attachment_files()`

`wp-includes/post.php:6846-6860` (released 7.0.2 — byte-identical in trunk at `:7023-7037`), reached
from `wp_delete_attachment()`:

```php
	if ( is_array( $backup_sizes ) ) {
		$del_dir = path_join( $uploadpath['basedir'], dirname( $meta['file'] ) );      // attacker-controlled DIRECTORY

		foreach ( $backup_sizes as $size ) {
			$del_file = path_join( dirname( $meta['file'] ), $size['file'] );          // attacker-controlled TARGET

			if ( ! empty( $del_file ) ) {
				$del_file = path_join( $uploadpath['basedir'], $del_file );

				if ( ! wp_delete_file_from_directory( $del_file, $del_dir ) ) {
					$deleted = false;
				}
			}
		}
	}
```

`path_join()` returns `$path` unchanged whenever it is absolute:

```php
function path_join( $base, $path ) {
	if ( path_is_absolute( $path ) ) {
		return $path;
	}
	return rtrim( $base, '/' ) . '/' . $path;
}
```

and `wp_delete_file_from_directory()` only checks

```php
	if ( false === $real_file || false === $real_directory
		|| ! str_starts_with( $real_file, trailingslashit( $real_directory ) ) ) {
		return false;
	}
```

Since `$real_directory` is derived from the same attacker-controlled `$meta['file']` as
`$real_file`, the containment test always passes. Compare the `sizes`, `original_image`,
`source_image` and `animated_video*` branches in the same function — they all build their
confinement directory from `$file = get_attached_file()`, which the attacker does **not** control.
Only the `$backup_sizes` branch is broken.

## Steps To Reproduce:

Lab: `cp -a` of the clean WordPress 7.0.2 template + Gutenberg 23.6.0 activated, own DB `media356`,
`php -S 127.0.0.1:8356`, base URL `http://localhost:8356`. Users `admin`, `author1` (Author),
`contrib1` (Contributor). Auth = `author1`'s own application password — no administrator involvement.

## Honest limits

I would rather state these than have you find them.

* **The re-install step was not executed.** I observed `wp-config.php` gone and
  `GET / -> 302 http://localhost:8356/wp-admin/setup-config.php`. Completing the installer would have
  destroyed the lab database, so "unauthenticated visitor becomes administrator → RCE via the plugin
  editor" is the well-understood *consequence* of that state, argued rather than demonstrated. The
  deletion itself, the destruction of `wp-config.php` and the hand-off to the installer are all
  executed and quoted above.
* **The attacker must own the attachment.** `edit_media_item_permissions_check()` is a real check and
  it works: an Author is refused (`403 rest_cannot_edit`) against an Administrator's attachment, and a
  Contributor is refused (`403 rest_cannot_edit_image`) outright. Both controls are in Proof C. This is
  not a horizontal-IDOR claim; the attack runs entirely through an attachment the Author uploaded.
* **The laundering step needs the `image_editor-<id>` nonce.** It is not a secret from the attacker —
  WordPress prints it to the Author itself in the media popup and I quote the exact line that carries
  it — but it does mean the chain is five requests rather than two, and a site that somehow blocked
  `admin-ajax.php?action=image-editor` for Authors would break this particular route into
  `_wp_attachment_backup_sizes`. The write primitive in `finalize_item()` is unaffected either way.
* **`S:C` is a judgement call.** I claim it because a file outside the document root was deleted, which
  on shared hosting reaches another security authority. If you disagree, the vector is
  `AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H` = **8.8**, and nothing in the report depends on which of the two
  you pick.
* **On core trunk the endpoint is gated** by `is_ssl() || 'localhost' === $host || …`. My trunk lab is
  plain HTTP on `Host: localhost:8357`, i.e. the `'localhost' === $host` arm. I have therefore *not*
  demonstrated it on a non-`localhost` plain-HTTP trunk install, and I am not claiming it works there —
  the claim is that it is on by default for every HTTPS site, which is what `is_ssl()` says. The
  released Gutenberg plugin has no such gate at all, which is why the released half needs no caveat.
* I have not attempted to turn the deletion into a *write* primitive, and I am not claiming one.

## Exclusions considered

* **"Open API endpoints serving public data (including usernames and user IDs)."** Does not apply. The
  endpoint is authenticated and gated (`upload_files` + `edit_post`), it returns no site data, and the
  finding is a **write/destroy** primitive, not a disclosure. The same-client controls in Proof C show
  the gate is genuinely enforced for callers who do not own the object — this is not an open endpoint.
* **"Users with administrator or editor privileges can post arbitrary JavaScript."** Does not apply on
  two counts: no JavaScript is claimed in this report at all, and the attacker is an **Author**, with
  the role evidenced in the proof output rather than asserted — `author1 upload_files=true`,
  `author1 unfiltered_html=false`, `contrib1 upload_files=false`.
* **"Denial of service."** The availability consequence here is not volumetric: it is the deletion of
  specific, attacker-named files, including `wp-config.php`. That is arbitrary file deletion (CWE-73),
  which the program treats as a vulnerability class, not a resource-exhaustion report.
* **"Self-XSS", "text injection", "scanner output"** — none claimed.

## Relationship to my other report

`media-finalize-subsize-filename-admin-xss.md` uses the **same write primitive** (`finalize_item()`
storing `sub_sizes[].file` verbatim) but is a different vulnerability with a different sink and a
different fix: there the value flows into `get_media_item()` and breaks out of an unescaped `src`
attribute, and the primary fix is an `esc_url()` in `wp-admin/includes/media.php:1716` — an escaping
bug that pre-dates this endpoint and is exploitable independently of it. Here the value flows into
`wp_delete_attachment_files()` and the primary fix is in `wp-includes/post.php`. Please triage them
together if that is easier; I filed them separately so that neither of the two distinct fixes is lost.

## Recommendations

Two independent defects; both should be fixed.

1. **`finalize_item()` must not accept path components.** In both
   `wp-includes/rest-api/endpoints/class-wp-rest-attachments-controller.php:2828-2933` and
   `gutenberg/lib/media/class-gutenberg-rest-attachments-controller.php:749-845`, run every
   `$sub_size['file']` / `$sub_size['original_image']` through `wp_basename()` +
   `sanitize_file_name()` and reject values that change:

   ```php
   $name = wp_basename( (string) $sub_size['file'] );
   if ( '' === $name || $name !== sanitize_file_name( $name ) || $name !== $sub_size['file'] ) {
       return new WP_Error( 'rest_invalid_param', __( 'Invalid file name.' ), array( 'status' => 400 ) );
   }
   ```

   Add the same as a `validate_callback` on the `file` and `original_image` schema properties, and
   add an `image_size` enum `validate_callback` to `finalize` as `sideload` already has.

2. **Harden the sink regardless.** `wp-includes/post.php:6846-6860` (trunk `:7023-7037`) must derive
   the confinement directory from trusted data, not from `$meta['file']`:

   ```php
   $intermediate_dir = path_join( $uploadpath['basedir'], dirname( _wp_relative_upload_path( $file ) ) );
   foreach ( $backup_sizes as $size ) {
       $del_file = path_join( $intermediate_dir, wp_basename( $size['file'] ) );
       wp_delete_file_from_directory( $del_file, $intermediate_dir );
   }
   ```

   This mirrors what every other branch of `wp_delete_attachment_files()` already does. Consider also
   making `wp_delete_file_from_directory()` refuse an absolute `$file` that is not already inside
   `$directory` before `realpath()`, so a future caller cannot reintroduce the same bug.

3. Optionally, sanitize on read: have `wp_update_attachment_metadata()` reject `file`,
   `original_image`, `source_image`, `animated_video*` and `sizes[*]['file']` values containing `/`,
   `\` or `..`.

## Prior art / duplicate check

**Verdict: known family, novel reachability — no matching public or disclosed report exists for the finalize-endpoint path.** Searched: WPScan, Patchstack and the CVE databases for "finalize_item / client-side media processing / wp_delete_attachment_files backup_sizes path traversal", the WordPress 7.0.3 (August 2026) fix list, and the classic 2018 arbitrary-file-deletion CVE.

The closest prior art is **CVE-2018-12895** (WordPress <= 4.9.6, "Authenticated Arbitrary File Deletion", fixed in 4.9.7). It shares the **sink** (`wp_delete_attachment_files()` -> `unlink()` on an attacker-influenced `_wp_attachment_metadata`) and the **impact model** (delete `wp-config.php` -> forced re-install -> RCE). It is nevertheless a different bug:

| | CVE-2018-12895 (2018, fixed 4.9.7) | This report |
|---|---|---|
| Metadata key abused | `thumb` | `file` (feeding the `$backup_sizes` confinement directory) |
| Entry point | `wp-admin/post.php?action=editattachment` (`$_POST['thumb']`) | `POST /wp/v2/media/<id>/finalize` (REST) |
| Branch of the sink reached | `thumb` branch | `$backup_sizes` branch — the only branch whose confinement directory is derived from attacker-controlled `$meta['file']` |
| What the 4.9.7 fix did | `basename()` on the `thumb` key | does not touch this branch or this key |
| Code involved | existed in 2018 | `finalize_item()` ships in released Gutenberg 23.6.0 and core trunk 7.1 — it did not exist in 2018 |

The 4.9.7 fix is key-specific and does not cover the `file` key or the `$backup_sizes` branch. Confirmed **not** among the 11-12 fixes in WordPress 7.0.3.

- CVE-2018-12895 (prior art, different key and entry point, fixed 4.9.7): https://wpscan.com/vulnerability/42ab2bd9-bbb1-4f25-a632-1811c5130bb4/ · https://www.rapid7.com/db/vulnerabilities/wordpress-cve-2018-12895/ · https://www.sonarsource.com/blog/wordpress-file-delete-to-code-execution/
- WordPress 7.0.3 fix list (this bug absent): https://patchstack.com/articles/wordpress-7-0-3-released-12-vulnerabilities-found-and-fixed/

HackerOne hacktivity cannot be enumerated without authentication, so an undisclosed duplicate cannot be ruled out with certainty.

## Impact

An Author-level account — the lowest role that can upload media, and a role routinely handed to
external contributors, freelancers and multi-author blogs — can delete **any file the PHP process can
unlink, anywhere on disk**:

1. **`wp-config.php` → site takeover.** WordPress then redirects every visitor to
   `wp-admin/setup-config.php` (observed). The first unauthenticated visitor can point the install at
   a database they control and become administrator, which reaches RCE through the plugin/theme
   editor. I observed the redirect; I did not complete the re-install.
2. `.htaccess` (removing uploads-directory hardening and PHP-execution blocks), mu-plugin security
   drop-ins, backups, or any other file the PHP user owns — **including, on shared hosting, files
   belonging to other tenants**, since the traversal leaves the uploads root and the document root
   entirely (proof B).
3. Destruction of site content and of the installation itself (availability).

No user interaction, no social engineering, five HTTP requests.
