## Vulnerability Details

Hi all,

I've discovered a heap out-of-bounds read in `curl_formadd` that causes libcurl to silently read past a caller-supplied buffer and transmit the leaked contents to the remote server. It's confirmed under ASan and reachable without violating any documented precondition.

## Impact

An application that passes a dynamically-computed length of `0` alongside a non-null-terminated buffer to `curl_formadd` will have libcurl read an unbounded number of bytes past the end of that allocation and include the overread data in the form submission. The practical scenario is an application that constructs multipart form fields from user input or file content, where an empty field name (zero bytes) is a valid state. In that case the application may legitimately pass `CURLFORM_NAMELENGTH, 0L` alongside a freshly allocated buffer that hasn't been null-terminated.

## Root cause

The problem is in `forminfo_copyfield` (`lib/formdata.c:121`):

```c
static CURLcode forminfo_copyfield(struct bufref *field, size_t len)
{
  const char *value = Curl_bufref_ptr(field);
  CURLcode result = CURLE_OK;

  if(value) {
    if(!len)
      len = strlen(value);           /* line 128 */
    result = Curl_bufref_memdup0(field, value, len);
  }

  return result;
}
```

The intent of the `if(!len)` branch is to handle the case where the caller didn't supply a length at all, so libcurl should derive it from the string. The problem is that `struct FormInfo` stores `namelength` as a plain `size_t`, zero-initialized, and there's no separate flag indicating whether the caller actually provided a value. Zero means both "not set" and "explicitly set to zero".

When `formadd_check` runs (`lib/formdata.c:264`) it passes `form->namelength` directly:

```c
if(!(form->flags & HTTPPOST_PTRNAME) &&
   forminfo_copyfield(&form->name, form->namelength))
  return CURL_FORMADD_MEMORY;
```

If the caller passed `CURLFORM_NAMELENGTH, 0L`, `form->namelength` is 0, and `forminfo_copyfield` falls through to `strlen(value)`. If `value` points to a buffer that was never null-terminated (say, a `malloc(8)` whose bytes are all `0x41`), `strlen` walks past the end of the allocation until it finds a null byte. Whatever it reads gets duplicated into the form part and sent to the server.

Note also that the `CURLFORM_NAMELENGTH` handler in `formadd` (`lib/formdata.c:380`) treats a nonzero stored value as "already set" for the duplicate-option check:

```c
if(curr->namelength)
    retval = CURL_FORMADD_OPTION_TWICE;
else
    curr->namelength = (size_t)form_int_arg(long);
```

So passing `CURLFORM_NAMELENGTH, 0L` stores 0, skips the duplicate check, and leaves no trace that the option was explicitly provided.

## Fix direction

Add a set of boolean flags to `struct FormInfo` to record whether each length field was explicitly provided by the caller (`namelength_set`, `contentslength_set`, `bufferlength_set`). Set the flag in the `formadd` switch when the option is seen, regardless of the value. In `forminfo_copyfield` (or in `formadd_check` before the call), only fall back to `strlen` when the flag is absent. When the flag is set and the length is 0, pass 0 directly and skip the `strlen` entirely. That's a zero-byte copy, which is the caller's intent.

An alternative is to use a sentinel (e.g., `SIZE_MAX` meaning "not set") and store the real value including 0 directly, but the boolean-flag approach is less likely to interact badly with the existing `CURL_FORMADD_OPTION_TWICE` checks.
