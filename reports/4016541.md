## Summary

**`CURLOPT_SSL_CTX_FUNCTION`'s man page prescribes `CURLOPT_FORBID_REUSE` as the remedy for callback
state leaking between transfers. That remedy does not work.** The run below sets it, and
`CURLOPT_FRESH_CONNECT` as well, on both transfers, and the leak happens anyway.

What leaks is a client certificate identity. A TLS session established while a client certificate was
installed by the callback is cached under a key that cannot describe that identity, so a later
transfer on the same handle, **with no callback set at all**, resumes that session and authenticates
to the server as the first transfer's client identity.

The remedy fails because the documentation only ever describes the connection pool, and the carrier
here is the TLS session cache. `CURLINFO_NUM_CONNECTS` confirms transfer 2 used a brand new
connection.

## The bug

The session cache key is built by `ssl_peer_key_build()` at `lib/vtls/vtls_scache.c:228`. Its first
parameter is everything it can see:

```c
static CURLcode ssl_peer_key_build(struct ssl_primary_config *ssl,
                                   const struct ssl_peer *peer,
                                   const char *tls_id,
                                   char **ppeer_key)
```

Identity-bearing fields inside `struct ssl_primary_config` do contribute to the key: a client
certificate path contributes `:CCERT-`, a blob contributes `:CertBlob-`, the type contributes `:CT-`.

The callback is not in that struct. `lib/vtls/vtls_config.h`:

```c
struct ssl_primary_config {          /* line 32 */
  ...
  BIT(native_ca_store);              /* line 57 */
  BIT(cache_session);
  BIT(deep_copy);
};

struct ssl_config_data {             /* line 62 */
  struct ssl_primary_config primary;
  ...
  curl_ssl_ctx_callback fsslctx;     /* line 65, outside primary */
  void *fsslctxp;                    /* line 66, outside primary */
};
```

So a client certificate installed through the callback is structurally incapable of entering the
session key. Two transfers with different client identities produce byte-identical keys, and the
second resumes the first's session.

#include <stdio.h>
#include <string.h>
#include <curl/curl.h>
#include <openssl/ssl.h>
static size_t sink(void *p, size_t s, size_t n, void *u){ (void)p;(void)u; return s*n; }
static CURLcode install_alice(CURL *c, void *sslctx, void *parm)
{
  SSL_CTX *ctx = (SSL_CTX *)sslctx; (void)c; (void)parm;
  if(SSL_CTX_use_certificate_file(ctx, "alice.crt", SSL_FILETYPE_PEM) != 1) return CURLE_ABORTED_BY_CALLBACK;
  if(SSL_CTX_use_PrivateKey_file(ctx, "alice.key", SSL_FILETYPE_PEM) != 1) return CURLE_ABORTED_BY_CALLBACK;
  return CURLE_OK;
}
int main(int argc, char **argv)
{
  int nocache = (argc > 1 && !strcmp(argv[1], "nocache"));

The second block is the control. One option changes, `CURLOPT_SSL_SESSIONID_CACHE = 0`, and transfer
2 becomes `NO-CLIENT-CERT`. That identifies the session cache as the carrier. The connection pool was
already excluded by `CURLOPT_FORBID_REUSE`, `CURLOPT_FRESH_CONNECT` and `CURLINFO_NUM_CONNECTS`
reporting a new connection.

## Prior work

Commit `7be1e70cb6` (2026-08-25), a week before 8.22.0:

> vtls: move 'native_ca_store' ssl_config_data => ssl_primary_config
>
> And include it as key for connection reuse matching.

That shipped as CVE-2026-80231 (Low). `native_ca_store` is at line 57 and `fsslctx` at line 65 of the
same struct in the same file. curl moved one field in and issued an advisory for having left it out.
The field that installs a client certificate was not moved.

curl has also published this exact outcome twice, both High: CVE-2016-5419 and CVE-2017-7468, both
"TLS session resumption client cert bypass". Those concerned the certificate set through
`CURLOPT_SSLCERT`. This is the same outcome reached through the callback, which is the one route that
cannot enter the session key.

`lib/vtls/vtls_scache.c` has not been modified since 8.22.0 was released. On master `fsslctx` was
moved again by `19eec5f639` "ssl: dedup ssl_fsslctx" (2026-09-08), from `ssl_config_data` into
`urldata.h`. That commit is a deduplication, does not touch the session cache key, and leaves the
callback outside `ssl_primary_config`, so this still applies.


## Severity

Medium. curl graded the same outcome High in CVE-2016-5419 and CVE-2017-7468, but those affected the
ordinary `CURLOPT_SSLCERT` path. Reaching it through the callback is a narrower population.

## Fix

Make the callback part of the session cache key. Either move `fsslctx` and `fsslctxp` into
`struct ssl_primary_config`, the way `native_ca_store` was moved in `7be1e70cb6`, so
`ssl_peer_key_build()` can include them, or do not cache a session at all when a
`CURLOPT_SSL_CTX_FUNCTION` callback was in effect for the handshake.

Including the two pointers in the key separates two different callbacks, but it will not separate one
callback that installs different certificates on different calls. Not caching sessions established
under a callback is the conservative option and the only one correct in that case.

Whichever is chosen, `CURLOPT_SSL_CTX_FUNCTION.md` should say that `CURLOPT_FORBID_REUSE` does not
cover TLS session resumption, because that is what a reader takes from it today.

## Impact

## Impact

An application that uses one easy handle for more than one purpose gets requests authenticated with
a client identity they never presented. A request meant to be anonymous, or to run as a different
principal, reaches the server carrying the earlier transfer's verified certificate identity. The
server cannot tell: from its side this is a properly resumed session with an authenticated client.

Reusing an easy handle across transfers is how libcurl is meant to be used, and installing a client
certificate from `CURLOPT_SSL_CTX_FUNCTION` is a supported pattern.
