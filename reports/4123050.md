## Vulnerability Details

## Summary:
The CVE-2026-11586 fix (849317ff5c, "ws: make pong sending lazy") adds the automatic PONG only when the WebSocket send buffer has room, but it put that check in ws_flush() (lib/ws.c:1712). curl_ws_recv(), the receive call of the documented CONNECT_ONLY model, still calls ws_enc_add_pending() without it at the end of every call that returns a frame (lib/ws.c:1694-1698 in 8.23.0, unchanged in master). Once the server stops reading and the 128 KB send buffer is full, that call appends the 6-byte PONG for an empty PING (ws.c:973) and returns CURLE_AGAIN before it clears ws->pending, because ws_enc_write_payload() refuses even a 0-byte payload when the buffer is full (ws.c:1010), so the next call appends the same PONG again. From then on every frame the application receives adds 6 bytes that are neither sent nor freed while the server does not read, even if the server sends no more PINGs, which is the unbounded growth CVE-2026-11586 describes, reached through the other documented API. Against the same server, a CONNECT_ONLY client with default options kept growing until the end of every run on 8.23.0 and master on Linux, and on 8.23.0 and 8.21.0 natively on macOS (about 345 MB of heap in 30 seconds), while CURLWS_NOAUTOPONG, the 8.23.0 curl tool (callback mode, which the fix covers) and 8.23.0 with the fix below stayed flat. The call in curl_ws_recv() came with 0b09132877, the advisory's Introduced-in commit, and the fix's test (test_20_11_crazy_pings) runs the curl tool, so only the callback path was checked.

## Affected version
8.21.0 to 8.23.0 and master, which is every release with the CVE-2026-11586 fix. ws_enc_add_pending(), ws_enc_add_frame() and ws_enc_write_payload() are byte-identical in 8.21.0, 8.22.0 and 8.23.0, and all three end curl_ws_recv() with the unguarded call (39b06935be added `!ws->using_reader` to its condition in 8.23.0, but using_reader is never set in CONNECT_ONLY mode, ws.c:1469-1486). lib/ws.c and lib/bufq.c are unchanged from 8.23.0 to today's master 59d2537b40. Earlier versions are covered by CVE-2026-11586.

Tested with release builds (no sanitizers): on Linux, curl-8_23_0, curl-8_23_0 with the fix below, and master 629646d9b7 (same lib/ws.c and lib/bufq.c as 59d2537b40), with OpenSSL in a Debian 12 container over TCP on 127.0.0.1 (amd64 under emulation on an Apple silicon Mac); natively on macOS 27.0.1, curl-8_23_0 and curl-8_21_0 over a Unix socket.

## Steps To Reproduce:
Linux with glibc 2.33 or later (the client uses mallinfo2()), everything on 127.0.0.1, files from the attached zip; linux/*.sh have the exact commands behind the numbers below.

1. Build a static libcurl without optional dependencies, so the client links with OpenSSL and zlib only: `cmake -S curl -B build -DCMAKE_BUILD_TYPE=Release -DCURL_USE_OPENSSL=ON -DBUILD_SHARED_LIBS=OFF -DBUILD_TESTING=OFF -DBUILD_EXAMPLES=OFF -DBUILD_LIBCURL_DOCS=OFF -DBUILD_MISC_DOCS=OFF -DCURL_USE_LIBPSL=OFF -DUSE_LIBIDN2=OFF -DCURL_USE_LIBSSH2=OFF -DUSE_NGHTTP2=OFF -DCURL_BROTLI=OFF -DCURL_ZSTD=OFF -DCURL_DISABLE_LDAP=ON && cmake --build build`
2. `cc -O2 poc/ws_recv_client.c -Icurl/include build/lib/libcurl.a -lssl -lcrypto -lz -lpthread -o ws_recv_client`. A plain CONNECT_ONLY client: curl_ws_recv() in a loop with poll() on CURLE_AGAIN, as curl_ws_recv(3) says. It never sends anything itself and prints RSS and heap in use every second.
3. `python3 poc/ws_noread_server.py 25001 185 &`. The server completes the handshake, never reads again, and sends empty PING and empty TEXT frames.
4. `./ws_recv_client ws://127.0.0.1:25001/ 180`. At first the PONGs only fill the TCP send path (about 30 seconds in my emulated container); after that heap and RSS grow by about 6 bytes per frame until the end.
5. Controls, each against a fresh server: `./ws_recv_client ws://127.0.0.1:25002/ 150 noautopong` and the curl tool, `build/src/curl -s -o /dev/null ws://127.0.0.1:25003/`. Both stay flat.

On macOS the same two files work over a Unix socket, where the growth starts at once: `python3 poc/ws_noread_server.py /tmp/ws.sock 35 &` and `UNIX_SOCKET=/tmp/ws.sock ./ws_recv_client ws://localhost/ 30` (link line in macos/run_macos.sh).

## Fix
In curl_ws_recv(), call ws_flush() instead of ws_enc_add_pending(): ws_flush() adds the pending PONG only when the send buffer has room, as the CVE-2026-11586 fix intended (fix/ws-recv-pong-guard.diff applies to 8.23.0 and master; 02-fix-check.txt is 8.23.0 with it).

AI disclosure: I used an AI assistant (Claude) for code review, test setup and drafting. I reproduced every result myself on curl built from the curl-8_23_0 and curl-8_21_0 tags and from master, on Linux and macOS; the attached logs are the raw output.

## Impact

A malicious WebSocket server can make any libcurl application that uses the documented CONNECT_ONLY model (curl_ws_recv()) with default options keep allocating memory, without limit, for as long as the connection is open, which is what the CVE-2026-11586 fix was meant to stop. The server completes a normal handshake, stops reading and sends small frames: once the TCP send path is full, every frame the application receives costs 6 bytes that stay allocated, three times the 2 bytes of an empty TEXT frame, and after the first stuck PONG the server does not need to send any more PINGs. The growth only depends on how many frames the server sends and the application reads; natively on macOS that was about 345 MB in 30 seconds. In #3788931 jimfuller2024 named long-lived libcurl applications with WebSocket connections to untrusted peers, such as services that proxy or aggregate WebSocket feeds, as the main concern; when they use curl_ws_recv(), the fix does not protect them. The curl tool is not affected because it uses the callback model that the fix covers, and CURLWS_NOAUTOPONG avoids the problem.
