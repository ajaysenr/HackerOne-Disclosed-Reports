## Vulnerability Details

## Summary

A zero-length `RELAY_END` cell can trigger a heap out-of-bounds read when the cell is copied through Conflux out-of-order delivery and then processed on a non-open AP stream.

Tor explicitly allows zero-length `RELAY_END` cells by treating them as `END_STREAM_REASON_MISC`, but `connection_ap_process_end_not_open()` reads `msg->body[0]` before checking `msg->length`.

This is normally masked by relay-cell backing storage. Conflux out-of-order queuing copies messages into exact-size heap allocations using `relay_msg_copy()`. For `msg->length == 0`, the copied `msg->body` points immediately after the allocation, and the unguarded `get_uint8(msg->body)` becomes a true heap OOB read.

## Affected Code

- `src/core/or/relay.c:846`

```c
int reason = get_uint8(msg->body);
```

The length check occurs later:

```c
if (msg->length == 0) {
  reason = END_STREAM_REASON_MISC;
}
```

- `src/core/or/conflux.c:923`

```c
c_msg->msg = relay_msg_copy(msg);
```

- `src/core/or/relay_msg.c:71`

```c
void *alloc = tor_malloc_zero(sizeof(relay_msg_t) + msg->length);
```

## Proof of Concept 

I added a local ASan regression PoC as a patch to this checkout. The relevant patched files are:

- `src/test/test_relaycell.c`
- Test name: `relaycell/end_cell_conflux_copy_oob`

{F5843197}  contains the `test_relaycell_end_cell_conflux_copy_oob()` test and its `copy_msg_through_conflux_ooo()` helper.

The PoC:

1. Builds a zero-length `RELAY_END` message for a non-open AP stream.
2. Sends it through Tor's actual `conflux_process_relay_msg()` out-of-order queue.
3. Dequeues the exact heap-backed `relay_msg_t` produced by `relay_msg_copy()`.
4. Simulates Conflux ordered delivery into `connection_edge_process_relay_cell()`.
5. ASan reports a heap-buffer-overflow at `connection_ap_process_end_not_open()`.

## Suggested Fix

Read the reason byte only when one is present:

```c
int reason = msg->length > 0 ? get_uint8(msg->body)
                             : END_STREAM_REASON_MISC;
```

## Impact

An attacker who can cause a zero-length `RELAY_END` to be queued out-of-order on a Conflux circuit can trigger a remote heap OOB read in Tor's relay-cell handling path. In ASan or hardened builds this is a reliable process crash. In non-ASan builds, this remains memory-unsafe behavior and reads from heap-adjacent memory.

The strongest reachable case is a non-open AP stream, such as a stream still in `AP_CONN_STATE_CONNECT_WAIT`, receiving an empty `RELAY_END` from the exit side after Conflux has copied the cell through the out-of-order queue.

Vector: `CVSS:3.0/AV:N/AC:H/PR:N/UI:N/S:U/C:N/I:N/A:H`

Justification:

1. `AV:N`: the malformed relay cell can be delivered over the Tor network.
2. `AC:H`: exploitation requires a linked Conflux pair, an out-of-order sequence gap, and a non-open AP stream state such as `AP_CONN_STATE_CONNECT_WAIT`.
3. `PR:N`: the attacker does not need privileges on the target client; they act as a relay/exit capable of sending relay cells on the circuit.
4. `UI:N`: after the circuit and stream exist, no additional user interaction is required to send the malformed `RELAY_END`.
5. `S:U`: the impact is within the vulnerable Tor process.
6. `C:N`: no direct information disclosure primitive is demonstrated.
7. `I:N`: the OOB byte is overwritten with `END_STREAM_REASON_MISC` for zero-length messages before meaningful reason handling.
8. `A:H`: ASan/hardened builds reliably abort the Tor process on the heap OOB read.
