## Vulnerability Details

**Repository:** [`monero-project/monero`](https://github.com/monero-project/monero) — `src/wallet/wallet_rpc_server.cpp`. Affected branch: `master` (commit `230de3794`, 2026-04-20).

## Summary

`monero-wallet-rpc` exposes a `relay_tx` JSON-RPC method. The handler `on_relay_tx` (lines 1926–1970) deserializes a caller-supplied hex blob into a `wallet2::pending_tx` structure and hands it directly to `wallet2::commit_tx` without any ownership check. Two things are missing.

First, there is no `m_restricted` guard. Every other transfer-class method — `transfer`, `sweep_all`, `transfer_split`, `sign_transfer`, `submit_transfer`, `sweep_dust` — gained one in commit `604bb05d8` (PR #10378, "fix: return early in sensitive methods for --restricted-rpc", merged 2026-03-23). `on_relay_tx` was not touched. So a caller holding only restricted credentials can invoke `relay_tx` freely.

Second, nothing in the handler checks that the `pending_tx` was ever produced by this wallet. `commit_tx` trusts every field verbatim: `selected_transfers` (which outputs to mark spent), `tx_key` (written into `m_tx_keys[txid]`), `dests` / `change_dts` / `construction_data` (written into `m_unconfirmed_txs[txid]`), and the per-transfer multisig nonce (`m_multisig_k`). A caller who can submit a pending_tx blob containing a valid on-chain transaction — their own funds will do — but with `selected_transfers` pointing at the *victim's* output indices can freeze those outputs and plant their own tx_key in the victim's key store.

Vulnerable handler, `src/wallet/wallet_rpc_server.cpp`:

```cpp
bool wallet_rpc_server::on_relay_tx(const wallet_rpc::COMMAND_RPC_RELAY_TX::request& req,
    wallet_rpc::COMMAND_RPC_RELAY_TX::response& res, epee::json_rpc::error& er,
    const connection_context *ctx)
{
    if (!m_wallet) return not_open(er);
    // ← no m_restricted check here

    cryptonote::blobdata blob;
    if (!epee::string_tools::parse_hexstr_to_binbuff(req.hex, blob)) { ... }

    tools::wallet2::pending_tx ptx;
    try {
        binary_archive<false> ar{epee::strspan<std::uint8_t>(blob)};
        if (::serialization::serialize(ar, ptx))
            loaded = true;
    } catch(...) {}

    try { m_wallet->commit_tx(ptx); }   // ptx fully attacker-controlled
    catch(const std::exception &e) { ... }
    ...
}
```

For comparison, every sibling handler added the guard in the same commit:

```cpp
// from on_transfer, on_sweep_all, on_submit_transfer, etc.
if (m_restricted)
{
    er.code = WALLET_RPC_ERROR_CODE_DENIED;
    er.message = "Command unavailable in restricted mode.";
    return false;
}
```

`commit_tx` itself (`wallet2.cpp`, lines 7572–7653) then performs the state mutations on whatever indices the blob specifies, with only a bounds check — not an ownership check — against the wallet's transfer list:

```cpp
// After sendrawtransaction succeeds:
for (size_t idx: ptx.selected_transfers)
    THROW_WALLET_EXCEPTION_IF(idx >= m_transfers.size(), ...);  // bounds only, no key-image match

add_unconfirmed_tx(txid, ptx.tx, ...);            // poisons m_unconfirmed_txs

if (store_tx_info() && ptx.tx_key != crypto::null_skey)
    m_tx_keys[txid] = ptx.tx_key;                 // plants attacker key in victim store

for (size_t idx: ptx.selected_transfers)
    set_spent(idx, 0);                            // freezes victim outputs

for (size_t idx: ptx.selected_transfers) {
    memwipe(m_transfers[idx].m_multisig_k.data(), ...);
    m_transfers[idx].m_multisig_k.clear();        // destroys multisig nonces permanently
}
```

There is no check that `m_transfers[idx].m_key_image` appears anywhere in `ptx.tx.vin`. The attacker ships their own valid transaction (spending their own outputs) but tells commit_tx that the victim's outputs were selected. The daemon accepts the transaction because it is cryptographically valid; the mismatch only matters inside wallet memory.

## Releases Affected

`master @ 230de3794` (2026-04-20). The missing guard is specific to this handler; the restricted-RPC framework itself is older. PR #10378 (merged 2026-03-23) is the most recent related work and is the change that left `on_relay_tx` unguarded while patching its siblings.

1. Starts `monerod --regtest --fixed-difficulty 1 --offline` on loopback.
2. Creates two wallets: `wallet_a` (attacker, unrestricted) and `wallet_b` (victim, `--restricted-rpc`).

## Possible Solution

Add the same two-line guard that all sibling handlers have, immediately after the `!m_wallet` check:

```cpp
bool wallet_rpc_server::on_relay_tx(...)
{
    if (!m_wallet) return not_open(er);
    if (m_restricted)
    {
        er.code = WALLET_RPC_ERROR_CODE_DENIED;
        er.message = "Command unavailable in restricted mode.";
        return false;
    }
    ...
```

That alone closes the bypass. The deeper issue — that `commit_tx` trusts `selected_transfers` without verifying those indices against the transaction's actual key images — is harder to fix safely because `commit_tx` is also called from legitimate paths where the wallet built the transaction itself. A straightforward defence-in-depth fix for the `relay_tx` path specifically is to cross-check before calling `commit_tx`:

```cpp
// Reject if selected_transfers count doesn't match actual inputs
if (ptx.selected_transfers.size() != ptx.tx.vin.size()) {
    er.code = WALLET_RPC_ERROR_CODE_BAD_TX_METADATA;
    er.message = "selected_transfers count does not match tx inputs";
    return false;
}
for (size_t i = 0; i < ptx.selected_transfers.size(); ++i) {
    size_t idx = ptx.selected_transfers[i];
    if (idx >= m_wallet->get_num_transfer_details()) {
        er.code = WALLET_RPC_ERROR_CODE_BAD_TX_METADATA;
        er.message = "selected_transfers index out of range";
        return false;
    }
    const auto &td = m_wallet->get_transfer_details(idx);
    const auto &vin = boost::get<cryptonote::txin_to_key>(ptx.tx.vin[i]);
    if (td.m_key_image != vin.k_image) {
        er.code = WALLET_RPC_ERROR_CODE_BAD_TX_METADATA;
        er.message = "selected_transfers key image mismatch";
        return false;
    }
}
```

Also worth adding `CHECK_IF_BACKGROUND_SYNCING()` for consistency with how the other state-mutating handlers are guarded.

## Impact

An operator running `monero-wallet-rpc` with `--restricted-rpc` — the intended safe mode for giving a monitoring agent, payment integration, or CI pipeline read-only-ish access — gets no protection against this method. Any process with restricted credentials can call `relay_tx` and trigger `commit_tx` on an attacker-crafted blob.

If the attacker can broadcast a valid transaction (their own funds), they get two concrete impacts against the victim wallet. First, `commit_tx` calls `set_spent()` on whichever transfer indices the blob specifies. Those outputs are permanently marked spent in the wallet cache and will not be selected for future transactions until `rescan_blockchain` is run. On a hot wallet processing payments, this freezes funds and causes sends to fail. Second, `commit_tx` stores the attacker's `tx_key` in the victim's `m_tx_keys[txid]`. Any call to `get_tx_key` or `get_tx_proof` for that txid returns attacker-controlled key material. A merchant using `get_tx_proof` to verify that a payment was sent will receive a proof that verifies correctly against the txid but was generated with a key the merchant did not create — enough to forge payment confirmation in any system that trusts wallet-rpc proofs.

The multisig impact is worse: `commit_tx` wipes `m_multisig_k` for the selected indices unconditionally. Those per-transfer signing nonces cannot be regenerated. An active multisig signing round that relied on them is permanently broken; the cosigners would need to re-export and re-import keys.
