# Title
Stored XSS via SVG Upload — check_content() Blocklist Bypass & 256-Byte Scan Limit (Self-Propagating Worm)

---

# Description

**Tested Version:** phpBB `4.0.0-a2-dev` (Docker, latest master branch as of March 2026)

phpBB implements a content-scanning check (`phpbb\files\filespec_storage::check_content()`) to prevent upload of malicious files. Two critical, independently exploitable flaws exist:

**Flaw 1 — Incomplete Blocklist (`phpbb/files/upload.php`, line 29):**
The `$disallowed_content` array does not include SVG-specific XSS vectors:
```php
protected $disallowed_content = array('body', 'head', 'html', 'img', 'plaintext', 'a href', 'pre', 'script', 'table', 'title');
```
Tags such as `<svg onload="">` and `<animate onbegin="">` are absent, so a valid SVG with an `onload` event passes the check and is stored on disk.

**Flaw 2 — 256-Byte Read Limit (`phpbb/files/filespec_storage.php`, line 364):**
```php
$ie_mime_relevant = fread($fp, 256); // Only first 256 bytes are scanned
```
Padding any payload (including explicitly blocked tags like `<script>`) beyond the 256-byte boundary completely bypasses validation.

**Delivery Vector — Inline SVG Serving (`phpbb/storage/controller/attachment.php`):**
Uploaded SVG files are served with `Content-Disposition: inline` and `Content-Type: image/svg+xml`, causing the browser to render and execute embedded JavaScript when the attachment link is clicked.

**Non-Default Configuration Note:**
`.svg` is not in phpBB's default allowed extensions list. An administrator must explicitly permit it. Additionally, SVG must be assigned to a non-image extension group (e.g., "Documents") — assigning it to "Images" causes `getImageSize()` to reject it silently.

# Remediation

1. **Remove 256-byte limit:** Scan the full file, not just the first 256 bytes.
2. **Expand blocklist:** Add `svg`, `animate`, `set`, `foreignObject`, `use`, `onload`, `onbegin` to `$disallowed_content`.
3. **Force `Content-Disposition: attachment` for SVG:** Never serve SVG files inline — force a download instead of browser rendering.

## Impact

**Stored XSS — Self-Propagating Signature Worm **

**Honest Limitations:**
- `HttpOnly` cookies prevent `document.cookie` extraction.
- The `cur_password` field is required to change account credentials via UCP, preventing blind AJAX-based credential takeover.

**Actual Impact :**
The XSS fires in the victim's same-origin browser context, allowing the attacker's JS to silently make authenticated requests to any UCP endpoint that does **not** require `cur_password`. The Signature endpoint (`/ucp.php?i=ucp_profile&mode=signature`) is fully writable with CSRF tokens alone.

By changing the victim's Signature, **every post they have ever made** is instantly updated to embed the attacker's payload link. Any user who views a thread containing the victim's posts is exposed to the payload, which can in turn infect their signature. This creates an exponentially self-propagating XSS worm capable of compromising the entire forum userbase from a single infected post.
