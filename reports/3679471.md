## Vulnerability Details

## Summary

The Monero GUI wallet renders address book descriptions as `TextEdit.RichText` (HTML) in the transaction confirmation dialog (`TxConfirmationDialog.qml:299`) without HTML entity escaping. An attacker can craft a `monero:` URI or QR code with HTML markup in the `tx_description` parameter. When a victim adds this address to their address book and later sends a transaction to it, the injected HTML renders in the confirmation dialog - the last UI defense before irreversible fund transfer.

This enables UI spoofing where the attacker can display fake trust indicators (e.g., "+ VERIFIED EXCHANGE"), hide the real address with CSS, or inject misleading recipient labels to deceive the victim into confirming a transaction they would otherwise reject.

## Releases Affected

  * All versions through v0.18.4.6 (latest release)
  * All platforms (Linux, Windows, macOS) - the vulnerability is in platform-independent QML code
  * Both simple mode and advanced mode

```
monero:4AdUndXHHZ6cfufTMvppY6JwXNouMBzSkbLYfpAV5Usx3skxNgYeYTRJ5UzqtReoS44qo9mtmXCqY45DJ852K5Jv2684Rge?tx_description=<b><span style='font-size:18px;color:green'>+ VERIFIED EXCHANGE</span></b><br><span style='font-size:6px;color:transparent'>attacker controlled</span>
```

This URI can also be encoded as a QR code for physical/social engineering attacks.

## Step 2: Victim adds address to address book

  1. Victim opens Monero GUI → Address Book page
  1. Victim pastes the `monero:` URI (or scans QR code via `AddressBook.qml:354-359`)
  1. `AddressBook.qml:337` calls `walletManager.parse_uri_to_object(addressLine.text)`
  1. `WalletManager.cpp:421` returns `tx_description` without HTML escaping
  1. `AddressBook.qml:340` sets `descriptionLine.text = parsed.tx_description`
  1. Victim clicks "Add" → `addressBook.addRow()` at line 455 stores the HTML in the wallet

### Step 3: Victim sends a transaction

  1. Victim initiates a transaction to the saved address
  1. Transaction confirmation dialog opens (`TxConfirmationDialog.qml`)
  1. Line 305: `getDescription(recipient.address)` retrieves the unsanitized HTML description
  1. Line 309: `title = FontAwesome.addressBook + " " + addressBookName` - no HTML escaping
  1. Line 320: `return title + "<br>" + spacedaddress` - injected into HTML string
  1. Line 299: `textFormat: TextEdit.RichText` - rendered as HTML
  1. Victim sees fake trust indicators and confirms the transaction

## Supporting Material/References

  * Same attack vector (malicious `monero:` URI) was used in CVE-2021-3401 (`platformpluginpath` injection, patched at `main.cpp:214`), but that targeted a different sink. This report targets the TxConfirmationDialog RichText rendering - a separate vulnerability.
  * The QR code scan path (`AddressBook.qml:354-359`) provides an additional attack vector beyond URI pasting.
  * `NetworkAccessBlockingFactory` at `main.cpp:449-451` blocks outbound network requests from QML on Qt >= 5.12, preventing `<img src="http://attacker/...">` exfiltration. However, this does NOT prevent UI spoofing via HTML/CSS formatting, which is the primary impact of this finding.
  * Additional sinks with the same root cause (unsanitized data in RichText) exist at:
    - `pages/settings/SettingsLog.qml:198` - daemon console output
    - `components/LineEditMulti.qml:115` - text label
    - `components/LineEdit.qml:177` - text label

### Suggested fix

HTML-escape all dynamic content before inserting into RichText:

```javascript
// Add helper function
function escapeHtml(text) {
    return text.replace(/&/g, '&amp;')
               .replace(/</g, '&lt;')
               .replace(/>/g, '&gt;')
               .replace(/"/g, '&quot;')
               .replace(/'/g, '&#039;');
}

// TxConfirmationDialog.qml line 309 - fix:
if (addressBookName) {
    title = FontAwesome.addressBook + " " + escapeHtml(addressBookName);
}
```

Additionally, sanitize `tx_description` in `WalletManager.cpp:421` before returning to QML:

```cpp
*tx_description = QString::fromStdString(o.tx_description)
    .toHtmlEscaped();  // Qt built-in HTML escaping
```

## Impact

The transaction confirmation dialog is the last UI defense before irreversible cryptocurrency transfer. HTML injection here enables:

1. **Address label spoofing** - display "✓ Binance Hot Wallet" or "Kraken Deposit" next to the attacker's address, making the victim believe they are sending to a trusted exchange
2. **Visual deception** - use CSS (`font-size:1px; color:transparent`) to hide the real address while showing a fake trusted address in large visible text
3. **Trust indicator injection** - add green checkmarks, "VERIFIED" badges, or fake security labels that do not exist in the legitimate UI
4. **Information hiding** - use `display:none` or matching background colors to obscure portions of the legitimate dialog content

A successful attack results in the victim voluntarily confirming a transaction to the attacker's address, believing it to be a trusted recipient. Since Monero transactions are irreversible and pseudonymous, the funds are permanently lost with no recourse.

The attack scales through QR codes distributed on social media, forums, or printed materials - anywhere a Monero address might be shared.
