## Vulnerability Details

## Summary:
The program i open scope so i did ASN enumeration and found the following subdomains is owned by Essity ████████ . while checking the JavaScript file found that there is endpoint hidden from GUI but found in the code ████████/Account/Register . access it and found it publicly accessible and fully functional  , despite not being linked from the login page or any other part of the application. It requires no invitation, no approval, no client or supplier code, and performs no verification that the registrant is affiliated with Essity or with an existing supplier.

Using hackerone alias email i was able to register account and access the fully website 

The application's own API calls fired automatically on login: GET /vendor/Vendors returned HTTP 200 with a JSON array of real vendor numbers and names, confirming that the account is not sandboxed or limited to empty data. GET /vendor/Regions and GET /vendor/definitions also returned live data.

This means any unauthenticated party on the internet can provision themselves an account on an internal Essity procurement system and read supplier data.

## Impact

Any unauthenticated party on the internet can provision themselves a working account on an internal Essity procurement system, with no invitation, no approval, no supplier code, and no verification of affiliation. The only requirement is access to an email inbox.

An attacker with a supplier-facing account could also use it as a credible pretext for social engineering against Essity procurement staff, or against the suppliers whose identities the portal discloses.

The resulting account is not sandboxed. On login, the application's own API returned live vendor records (GET /vendor/Vendors, HTTP 200, JSON array of vendor numbers and names), along with reference data from /vendor/Regions and /vendor/definitions. The portal interface exposes Purchase Orders/Deliveries, Payments, and Blanket Orders, plus a Purchase Order search that queries the backend a search I submitted returned "please narrow your search," indicating the query reached a populated data set rather than an empty one.

I want to be precise about what I did and did not establish: I confirmed that vendor data is returned to a self-registered account, by observing the application's own automatic API calls. I did not browse, search, export, or open any records, and I did not test for write access or authorization flaws on any endpoint. The impact described above is based on what the application itself surfaced within seconds of login.
