## Vulnerability Details

## Vulnerability Details

This is an incomplete fix of the earlier `connclose()` mitigation (CVE-2026-80229). That change stops a connection that borrowed a private `OSSL_LIB_CTX` from going back into the connection pool. It does not keep the library context alive until the `SSL_CTX` that borrowed it is destroyed. On the multi interface the connection can sit in `multi->cshutdn` after the easy handle that owns the context has been freed.

Affected tree: curl `master` commit [`03f3f4c6d97be3c2c9ad42010f65e61bf0a2c05c`](https://github.com/curl/curl/commit/03f3f4c6d97be3c2c9ad42010f65e61bf0a2c05c) (`LIBCURL_VERSION` 8.23.1-DEV). Requires a build against OpenSSL 3 (`OPENSSL_HAS_PROVIDERS`). `curl_easy_perform()` is not affected. A normal engine id that `ENGINE_by_id()` accepts is not affected.

### Conditions

* `CURLOPT_SSLENGINE` is set to a name that is **not** an OpenSSL ENGINE id (`"default"`, a provider name, or a `provider:propq` string). `ossl_set_engine()` misses the ENGINE and falls through to `ossl_set_provider()`.
* The transfer uses the multi interface (`curl_multi_*`, or `curl --parallel`).
* The TLS peer does not finish `close_notify` inside the single non-blocking shutdown attempt done when the transfer completes. That is the normal case for an HTTP/1.1 server that was keeping the connection open. The connection then stays in `cshutdn` for up to `DEFAULT_SHUTDOWN_TIMEOUT_MS` (2 seconds), or until `curl_multi_cleanup()`.

### What the code does

1. The provider path allocates a library context and stores it only on the easy handle. There is no `OSSL_LIB_CTX_up_ref` anywhere in the tree. OpenSSL 3.0 has no such function, and `OSSL_LIB_CTX_free()` in 3.0.22 always destroys the object.

```c
/* lib/vtls/openssl.c, ossl_set_provider() */
if(!data->state.libctx) {
  OSSL_LIB_CTX *libctx = OSSL_LIB_CTX_new();
  if(!libctx)
    return CURLE_OUT_OF_MEMORY;
  /* ... optional propq ... */
  data->state.libctx = libctx;
}
```

2. The handshake builds the `SSL_CTX` with that pointer. OpenSSL 3.0.22 `SSL_CTX_new_ex()` only does `ret->libctx = libctx`. It does not take a reference. It also `EVP_MD_fetch()`es digests from that context. The only curl-side mitigation is `connclose()`, which sets `conn->bits.close` so the connection will not be reused.

```c
/* lib/vtls/openssl.c, Curl_ossl_ctx_init() */
octx->ssl_ctx =
#ifdef OPENSSL_HAS_PROVIDERS
  data->state.libctx ?
  SSL_CTX_new_ex(data->state.libctx, data->state.propq, req_method):
#endif
  SSL_CTX_new(req_method);

#ifdef OPENSSL_HAS_PROVIDERS
if(data->state.libctx)
  /* forbid connection reuse with provider/engine use */
  connclose(data->conn);
#endif
```

3. On a successful (not premature) completion, `multi_done_locked()` sees `bits.close` and returns `CPOOL_DO_CLOSE`. `cpool_discard_conn()` tries shutdown once. `ossl_shutdown()` starts with `SSL_read()`. If the peer has not sent `close_notify`, that returns `SSL_ERROR_WANT_READ`, `done` stays false, and the connection is queued on `multi->cshutdn`. The easy handle is detached. Later shutdown runs on `multi->admin`, which does not own this `libctx`. The pointer lives inside the `SSL_CTX`.

```c
/* lib/conncache.c, cpool_discard_conn() */
if(!done) {
  Curl_cshutdn_try_once(admin, conn, &done);
}
if(done || !data->multi)
  Curl_cshutdn_terminate(admin, conn, FALSE);
else
  Curl_cshutdn_add(&multi->cshutdn, multi, conn, max_shutdowns);
```

4. The usual application sequence after `CURLMSG_DONE` is `curl_multi_remove_handle()` plus `curl_easy_cleanup()`. The connection is already detached, so remove does not destroy it. `Curl_close()` then calls `Curl_ssl_close_all()` → `ossl_close_all()` → `ossl_provider_cleanup()`, which unloads the providers and frees the library context while `cshutdn` still holds the `SSL` / `SSL_CTX`.

```c
/* lib/url.c, Curl_close() */
if(!data->state.internal && data->multi)
  Curl_multi_remove_handle(data->multi, data);
/* ... */
Curl_ssl_close_all(data);   /* ossl_provider_cleanup() frees libctx */
```

```c
/* lib/vtls/openssl.c, ossl_provider_cleanup() */
if(data->state.baseprov) {
  OSSL_PROVIDER_unload(data->state.baseprov);
  data->state.baseprov = NULL;
}
if(data->state.provider) {
  OSSL_PROVIDER_unload(data->state.provider);
  data->state.provider = NULL;
}
OSSL_LIB_CTX_free(data->state.libctx);
data->state.libctx = NULL;
```

5. The next `curl_multi_perform()`, or `curl_multi_cleanup()`, drives `cshutdn`. `ossl_shutdown()` calls `SSL_read()` / `SSL_shutdown()` on that `SSL`, then `ossl_close()` calls `SSL_free()` and `SSL_CTX_free()`. Those calls use the `libctx` stored in the `SSL_CTX`. `SSL_read()` reaches `EVP_MD_fetch()` on it.

```c
/* lib/vtls/openssl.c, ossl_shutdown() */
if(!(SSL_get_shutdown(octx->ssl) & SSL_SENT_SHUTDOWN)) {
  ERR_clear_error();
  for(i = 0; i < 10; ++i) {
    nread = SSL_read(octx->ssl, buf, (int)sizeof(buf));
    if(nread <= 0)
      break;
  }
}
```

```c
/* lib/vtls/openssl.c, ossl_close() */
if(octx->ssl) {
  SSL_free(octx->ssl);
  octx->ssl = NULL;
}
if(octx->ssl_ctx) {
  SSL_CTX_free(octx->ssl_ctx);
  octx->ssl_ctx = NULL;
}
```

`curl_easy_perform()` does not hit this. `Curl_close()` runs `curl_multi_cleanup(data->multi_easy)` first, which drains `cshutdn` and destroys the `SSL_CTX` while the easy handle, and therefore the `libctx`, is still alive. A premature `curl_multi_remove_handle()` (`mstate < MSTATE_COMPLETED`) uses `CPOOL_DO_TERMINATE` and destroys the connection inside remove, still before `ossl_provider_cleanup()`.

### Confirmation

On OpenSSL 3.0.22, the same order as `ossl_provider_cleanup()` followed by `ossl_shutdown()` was executed after a completed TLS 1.3 handshake (`SSL_CTX_new_ex` on a private `libctx`, unload `default` and `base`, `OSSL_LIB_CTX_free`, then `SSL_read`):

* With the freed block left untouched, `SSL_read` returned. The allocation is small and is not unmapped, so the use-after-free is often silent.
* With `free()` quarantining the block (contents poisoned, pointer not reused), `SSL_read` segfaulted in `CRYPTO_THREAD_read_lock`, reached from `EVP_MD_fetch`. That is the first call `ossl_shutdown()` makes.

## Suggested fix

`connclose()` is not sufficient. `OSSL_LIB_CTX_up_ref()` is also not a portable fix: it does not exist in OpenSSL 3.0/3.1, and `OSSL_LIB_CTX_free()` there ignores any count and always destroys the context.

Keep a curl-owned reference on the context for as long as any `SSL_CTX` created from it exists. `curl_easy_cleanup()` drops only the easy handle's reference. `ossl_close()` drops the connection's reference **after** `SSL_CTX_free()`. The real `OSSL_PROVIDER_unload` / `OSSL_LIB_CTX_free` runs when the last reference goes away, including when that happens later on `cshutdn`. The same release is required on the QUIC cleanup path, which frees `SSL_CTX` without calling `ossl_close()`.

The two drops can happen on different threads (`curl_easy_cleanup` after `curl_multi_remove_handle`, versus `curl_multi_perform` on the multi handle), so the counter has to be atomic.

## Impact

An application that sets `CURLOPT_SSLENGINE` to an OpenSSL 3 provider (anything `ENGINE_by_id()` does not accept) and uses the multi interface in the normal way — wait for `CURLMSG_DONE`, remove the easy handle, `curl_easy_cleanup()`, keep using the multi handle — frees an `OSSL_LIB_CTX` that a live `SSL_CTX` on `multi->cshutdn` still borrows. The next multi perform or multi cleanup then calls `SSL_read` / `SSL_shutdown` / `SSL_free` on that freed context (CWE-416). A normal server that does not answer `close_notify` in the same non-blocking turn is enough to leave the connection queued; the default grace period is 2 seconds. The bug is not on by default and a remote peer cannot create the `libctx` by itself, but once the application has opted in, the use-after-free is the common shutdown path, not a rare race, and it corrupts memory inside the process that linked libcurl.
