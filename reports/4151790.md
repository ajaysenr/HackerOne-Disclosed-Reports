## Vulnerability Details

## Summary

`Public::BaseController` marks public board pages `Cache-Control: public,
max-age=30`. `allow_unauthenticated_access` skips only `require_authentication`,
so `resume_session` still runs and a signed-in visitor receives a response
carrying their own `current-user-id`, CSRF token, CSP nonce and timezone.
Nothing sets `Vary: Cookie`, so the edge stores that response under the URL
alone and serves it to every later requester for 30 seconds, cookies or not.

The CSP nonce is the part I would look at first. A nonce only does its job
while it is unpredictable per response; one handed to every visitor for 30
seconds is not.

## Steps to reproduce

The attached `poc.sh` runs the whole thing and prints its own verdict. It makes
four requests over about twelve seconds and needs only curl and grep.

1. On an account you own, create a board and turn on its Public link
   (Board → Edit → Public link).

2. In a directory with `poc.sh`, create two files:

   - `url.txt` — one line, the public board URL:
     `https://app.fizzy.do/<account>/public/boards/<key>`
   - `cookie.txt` — one line, your whole Cookie header for app.fizzy.do
     (DevTools → Network → any request → Request Headers → Cookie)

3. `bash poc.sh`

It uses two unrelated cache keys so each starts cold: a **control** key only
ever requested without cookies, and a second key requested first while signed
in and then twice with no cookies at all.

Three things read off that together:

- `vary` lists `Accept` and `Sec-Fetch-Site`. Not `Cookie`.
- Steps 2 and 3 are `HIT` with a rising `age`, byte-identical to step 1, and

  the signed-in response, not from the page.

## Impact

## Impact

For 30 seconds after any signed-in person opens a public board link, anyone
requesting that URL is served their response. From the output above, that
hands over:

- **`csp-nonce`** — shared across visitors for the cache window, so the nonce
  is no longer unpredictable while the entry lives. Any HTML injection
  reachable on that page would be scriptable against the policy for that
  window. I did not find such an injection and am not claiming one; what I am
  reporting is that the nonce stops being a per-response secret.
- **`current-user-id`** — identifies which Fizzy user opened the board, and
  yields a real user id. It appears three times: once as a meta tag and twice
  in the `user_css` block.
- **`timezone`** — the viewer's configured timezone.
- **`csrf-token`** — a per-session value. It is bound to the session cookie, so
  it is not usable without that cookie; I list it as a session value that
  should not be shared between visitors, not as a CSRF path.
- Anything in `flash[:notice]` or `flash[:alert]` for that session, which
  `layouts/shared/_flash` renders into the same page.

The board content itself is not the issue — it is published on purpose. What
leaks is who looked at it and what their session was carrying.

The only precondition is that a signed-in person opens the public link, which
is how these links are normally shared within a team.

## Where it comes from

`app/controllers/public/base_controller.rb`

```ruby
class Public::BaseController < ApplicationController
  allow_unauthenticated_access      # skips require_authentication;
                                    # resume_session still runs
  before_action :set_public_cache_expiration

  private
    def set_public_cache_expiration
      expires_in 30.seconds, public: true
    end
end
```

`app/views/layouts/public.html.erb` renders `layouts/shared/head` — which emits
`csrf_meta_tags`, `csp_meta_tag`, `current-user-id`, the timezone tag and
`layouts/shared/user_css` — and `layouts/shared/flash`.

## Suggested fix

Keep the cacheable response the one with nothing personal in it. Either render
public pages without a session, or keep the session and stop marking those
responses public:

```ruby
def set_public_cache_expiration
  if Current.identity
    expires_now
  else
    expires_in 30.seconds, public: true
  end
end
```

`Vary: Cookie` would also separate the entries, but at the cost of most of the
caching, since nearly every visitor carries some cookie.

## Notes

- Tested only against a board and an account I created myself, registered
  with a @wearehackerone.com address. Both the signed-in and the cookieless
  requests in the script are mine; no other user's data was accessed at any
  point.
- The board has been unpublished and the session signed out since.
- I also checked whether this reaches the paid apps and did not find it
  there: world.hey.com/<user> does send Cache-Control: max-age=60, public,
  but Cloudflare answers cf-cache-status: DYNAMIC for it and the anonymous
  response carries no csrf-token, csp-nonce or user id. app.basecamp.com and
  launchpad.37signals.com both answer no-cache.
