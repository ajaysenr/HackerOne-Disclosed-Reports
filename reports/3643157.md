## Vulnerability Details

## Summary

Multiple geometry functions perform out-of-bounds reads from heap memory when given 
crafted WKB input. The functions `num_geometries()` and `num_points()`
in `sql/spatial.cc` read 4 bytes via `uint4korr(m_data)` without first checking that
4 bytes are available in the buffer. When the input payload is shorter than 4 bytes,
the remaining bytes are read from adjacent heap memory and returned to the client as
part of the integer result. As such, each invocation can disclose up to 4 bytes of adjacent
heap memory.

The root cause is missing `no_data()` bounds checks. The safe version of the same
function (`Gis_geometry_collection::num_geometries()`) correctly performs this check
and returns an error. The affected functions skip it.

The input validation gateway `Geometry::construct()` (`sql/spatial.cc:346`) only verifies
that total input length >= 9 bytes and the geometry type ID is valid. It does not perform
structural validation of the payload. This means crafted hex literals in `SELECT`
statements bypass all validation and reach the vulnerable functions directly.

The MDEV-38372 fix added `is_binary_valid()` checking to `Field_geom::store()`
(the INSERT-into-column path), but this doesn't protect the direct-expression path
through geometry functions like `SELECT ST_NumGeometries(x'...')`.

## Environment

- MariaDB 12.2.2-MariaDB-deb12,
- MariaDB 12.2.2-MariaDB-asan-debug
- Debian 12 (Bookworm), x86_64
- Default installation, InnoDB, no special configuration

## Affected Code

**1. `Gis_multi_line_string::num_geometries()` - `sql/spatial.cc:3372`**

```c
int Gis_multi_line_string::num_geometries(uint32 *num) const
{
  *num= uint4korr(m_data);  // reads 4 bytes, no bounds check
  return 0;
}
```

The same bug exists in `Gis_multi_point::num_geometries()` and
`Gis_multi_polygon::num_geometries()`.

Compare with the safe version, `Gis_geometry_collection::num_geometries()`:

```c
int Gis_geometry_collection::num_geometries(uint32 *num) const
{
  if (no_data(m_data, 4))   // bounds check present
    return 1;
  *num= uint4korr(m_data);
  return 0;
}
```

**2. `Gis_line_string::num_points()` - `sql/spatial.cc:1695`**

```c
int Gis_line_string::num_points(uint32 *n_points) const
{
  *n_points= uint4korr(m_data);  // reads 4 bytes, no bounds check
  return 0;
}
```

**3. `Geometry::construct()` - `sql/spatial.cc:346` (no structural validation)**

```c
Geometry *Geometry::construct(Geometry_buffer *buffer,
                              const char *data, uint32 data_len)
{
  uint32 geom_type;
  Geometry *result;

  if (data_len < SRID_SIZE + WKB_HEADER_SIZE)   // only checks >= 9 bytes
    return NULL;
  geom_type= uint4korr(data + SRID_SIZE + 1);
  if (!(result= create_by_typeid(buffer, (int) geom_type)))
    return NULL;
  result->m_data= data+ SRID_SIZE + WKB_HEADER_SIZE;
  result->m_data_end= data + data_len;
  return result;  // no structural validation of payload
}
```

### PoC 2: Partial payload confirms heap bytes in returned value

```sql
SELECT ST_NumGeometries(x'0000000001050000004142');
```

2 payload bytes (`0x41 0x42` = "AB"). `num_geometries()` reads 4 bytes starting at
`m_data`: the first 2 are our input, the remaining 2 are read from past the allocation
boundary.

**Result on normal build**: Returns `805323329`, which decodes (little-endian) to bytes
`41 42 00 30`, our `AB` plus 2 bytes from adjacent heap memory (`0x00 0x30`).
This value is consistent across repeated runs.

**ASAN build**: Same crash as PoC 1, same stack trace.

### Control: GEOMETRYCOLLECTION returns NULL (has bounds check)

```sql
SELECT ST_NumGeometries(x'000000000107000000');
```

**Result**: `NULL`

`Gis_geometry_collection::num_geometries()` correctly calls
`no_data(m_data, 4)`, detects insufficient data, and returns an error. This confirms
the fix is simply adding the same bounds check to the affected functions.

### Additional affected geometry types (same bug, same result)

```sql
-- MULTIPOINT (type 4), same leak
SELECT ST_NumGeometries(x'000000000104000000');

-- MULTIPOLYGON (type 6), same leak
SELECT ST_NumGeometries(x'000000000106000000');
```

Both return the same leaked value as MULTILINESTRING, confirming that
`Gis_multi_point::num_geometries()` and `Gis_multi_polygon::num_geometries()`
have the same missing bounds check.

## Impact

## Heap Information Disclosure

The leaked 4 bytes come from heap memory adjacent to the input allocation. On a
non-ASAN production build, the leaked data is returned to the client as an
integer value. The contents of the leaked bytes depend on heap layout and what the 
allocator placed adjacent to the input buffer.

## Denial of Service (ASAN/debug builds)

On ASAN-instrumented builds, these queries crash the server immediately due to invalid
memory access.

## No Special Privileges Required

The vulnerability is triggered by a `SELECT` with a hex literal. No special table or
database privileges are required. Any authenticated user with permission to execute `SELECT`
statements can reach the vulnerable path.

## Affected Versions

Confirmed on 12.2.2. Source inspection of 10.6.25 shows the same vulnerable implementations
without bounds checks. As such, the issue likely affects all currently-maintained MariaDB versions.
